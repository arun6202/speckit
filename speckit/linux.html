Orientation

You know Windows. Here's the map.

You can ssh in and run ls. This manual takes you from there to confidently deploying and operating .NET services on the two distro families you'll actually meet in the enterprise: Oracle Linux (RHEL family — common under Oracle DB, OCI, corporate datacenters) and Ubuntu (Debian family — common on Azure, AWS, and developer machines). The five mental-model shifts

Most friction for a Windows developer isn't commands — it's five assumptions that quietly stop being true:

  • One tree, no drive letters. There is no C:\. Everything — disks, USB sticks, even network shares — is grafted ("mounted") somewhere under a single root /.
  • Everything is a file. Devices (/dev/sda), kernel state (/proc), sockets — readable and writable like files. There is no Registry; configuration is plain text in /etc.
  • Case matters, extensions don't. Program.cs and program.cs are different files. A file is executable because of a permission bit, not because it ends in .exe.
  • Text streams are the universal interface. PowerShell pipes .NET objects; bash pipes raw text. Small tools chained with | replace most GUI consoles.
  • Root ≠ Administrator-with-UAC. sudo elevates a single command, is logged, and is granted per-user. You almost never log in as root.

.NET corner

Your C# skills transfer almost completely: ASP.NET Core, EF Core, gRPC and console apps run natively on both distros. What changes is everything around the process — where files go, who owns them, how the service starts, which port it may bind. That's exactly what these 12 concepts cover.

Practice risk-free: enable WSL2 on your Windows machine (wsl --install -d Ubuntu) for the Ubuntu side, and run Oracle Linux free in a VirtualBox VM or an always-free OCI instance for the RHEL side. Same commands, zero fear of breaking a server.

Gotcha — line endings & case

Files edited on Windows carry CRLF endings; a bash script with CRLF fails with the baffling error /bin/bash^M: bad interpreter. Fix with dos2unix script.sh, and set git config core.autocrlf input. Also remember: appSettings.json ≠ appsettings.json on Linux — a classic first-deploy crash for ASP.NET devs.

Concept 01

Linux architecture

Three layers: user space (your apps, the shell, libraries like glibc), the kernel (process scheduling, memory, drivers, file systems — ~30M lines of code), and hardware. Apps never touch hardware directly; they make system calls that cross into privileged kernel mode. Same idea as Windows' user mode / NT kernel split — but on Linux the seams are visible and inspectable.

Deep dive: what actually happens on a syscall

When your .NET app calls File.ReadAllText, the runtime calls glibc's read(), which executes a special CPU instruction that switches the processor to privileged mode and jumps to a fixed kernel entry point. The kernel validates the request (permissions — Concept 03), talks to the file-system driver and the disk, copies data into your process's buffer, then drops back to user mode. This boundary is why a crashing app can't take the OS down — same philosophy as Windows user/kernel mode, enforced the same way by the CPU.

.NET corner

The .NET runtime ID linux-x64 assumes glibc — fine on both Oracle Linux and Ubuntu. Alpine containers use musl instead, which needs linux-musl-x64. When a published binary dies instantly with a cryptic loader error, mismatched C library is suspect #1 — check with ldd ./MyApp, which lists the native libraries your binary links (like Dependency Walker for Linux).

Concept 02

File system hierarchy

A standard layout for your own app

BothWhere a deployed .NET service should live
$ sudo mkdir -p /opt/orderapi              # binaries (self-contained vendor app)
$ sudo mkdir -p /etc/orderapi              # environment-specific config
$ sudo mkdir -p /var/log/orderapi          # file logs (if not using journald)
$ sudo mkdir -p /var/lib/orderapi          # app state/data the app writes
This separation is the Linux convention and it pays off: config survives redeploys, logs are where log rotation expects them, and backups can target /etc + /var/lib only. It's the moral equivalent of not writing into Program Files at runtime.
Gotcha — /tmp is not a parking lot

Both distros clean /tmp aggressively (Ubuntu on reboot; Oracle Linux additionally ages files out via systemd-tmpfiles after ~10 days). Never store anything you need there. Also: /proc and /dev consume no disk — don't be alarmed by their contents in du output; exclude them with du -xh.

.NET corner

ASP.NET Core resolves appsettings.json relative to the working directory, not the binary. When you later write the systemd unit (Concept 10), set WorkingDirectory=/opt/orderapi or your config silently won't load — the #1 first-deploy bug. Environment-specific overrides belong in /etc/orderapi and can be layered via ASPNETCORE_ENVIRONMENT + a config path, keeping secrets out of the deploy artifact.

Concept 03

File permissions & chmod

Every file has an owner, a group, and nine permission bits: read/write/execute for user (owner), group, and others. Simpler than Windows ACLs — and the cause of 90% of your early "Permission denied" errors, so learn to read them before you learn to change them.

Visual Guide: UNIX Permissions Map (e.g. 750)

Reading the wall of letters

BothDecode ls -l
$ ls -l /opt/orderapi/
-rwxr-x--- 1 orderapi orderapi 84512 Jun 10 09:14 OrderApi
-rw-r----- 1 orderapi orderapi  1311 Jun 10 09:14 appsettings.json
drwxr-x--- 2 orderapi orderapi  4096 Jun 10 09:14 wwwroot

 d rwx r-x ---
 │ │   │   └── others: nothing
 │ │   └────── group "orderapi": read + enter/execute
 │ └────────── owner "orderapi": read + write + execute
 └──────────── type: d=directory, -=file, l=symlink
Numerically: r=4, w=2, x=1 per triad → rwxr-x--- = 750. Common values: 755 (everyone can read/execute — binaries, public dirs), 644 (everyone can read — config), 600 (owner only — secrets, SSH keys), 750/640 (group-restricted service files).
Bothchmod & chown — the verbs
$ chmod +x deploy.sh                    # make a script runnable (symbolic)
$ chmod 640 appsettings.Production.json # numeric: owner rw, group r, others none
$ chmod u=rw,g=r,o= secrets.env         # symbolic equivalent of 640
$ sudo chown -R orderapi:orderapi /opt/orderapi   # owner:group, recursive
$ sudo chmod -R u=rwX,g=rX,o= /opt/orderapi       # capital X: execute only on dirs
On a directory, x means "may enter / traverse" and r means "may list". The capital-X trick sets execute on directories (so they're traversable) without making every data file executable — exactly what you want after copying a publish folder.
BothDiagnose a Permission denied in 20 seconds
$ namei -l /opt/orderapi/appsettings.json   # shows perms of EVERY path component
$ id                                        # my uid, gid, groups
$ sudo -u orderapi cat /opt/orderapi/appsettings.json   # test AS the service user
Access requires permission on the file and traverse (x) on every directory above it — namei -l reveals the broken link in the chain instantly. sudo -u svc cmd reproduces exactly what your service experiences.

Deep dive: umask, setuid and the sticky bit

umask decides default permissions for new files: with the usual umask 022, new files arrive as 644 and directories as 755. Services that write shared data sometimes need umask 027 set in their unit file.

setuid (chmod u+s, shows as rws) makes a binary run as its owner — it's how passwd edits root-owned files. Treat unexpected setuid binaries as a security red flag: find / -perm -4000 2>/dev/null.

The sticky bit on /tmp (drwxrwxrwt) means anyone may create files there but only owners may delete their own — why a world-writable /tmp isn't chaos.

Gotcha — never chmod 777

chmod -R 777 "fixes" the error and creates three new problems: any process can tamper with your binaries, SSH refuses keys in over-permissive dirs, and security scans flag the host. The correct fix is always ownership (chown to the service user) plus minimal bits (750/640). Relatedly: a private SSH key must be 600 or ssh will refuse it with UNPROTECTED PRIVATE KEY FILE.

.NET corner

After dotnet publish on Windows and copying to Linux, the apphost (./OrderApi) loses its execute bit — run chmod +x OrderApi (or launch via dotnet OrderApi.dll, which needs no bit). On Oracle Linux there's a second permission system: SELinux — if perms look right but access is still denied, jump to the SELinux block in Concept 09. Ubuntu's AppArmor rarely interferes with custom services.

Concept 04

Process management

Every process has a PID, a parent, and a state (running, sleeping, stopped, zombie). PID 1 — systemd — is the ancestor of everything. Where Windows gives you Task Manager and taskkill, Linux gives you a toolbox of small, composable views into the same process table.

Find, inspect, stop

BothThe hunting kit
$ ps aux | grep -i [d]otnet        # find your app ([d] trick excludes grep itself)
$ pgrep -af dotnet                 # cleaner: PIDs + full command line

ps aux columns to read: %CPU, %MEM, VSZ/RSS (virtual/actual memory), STAT (S=sleeping, R=running, Z=zombie, T=stopped), and the command. A high-CPU dotnet here plus htop's thread view (press H) is your first GC/spin diagnosis pass.
BothSignals — graceful first, force later
$ kill 4321            # sends SIGTERM (15): "please shut down cleanly"
$ kill -INT 4321       # SIGINT: same as pressing Ctrl+C in its terminal
$ kill -9 4321          # SIGKILL: kernel removes it, NO cleanup runs
$ pkill -f OrderApi     # signal by name pattern instead of PID
SIGTERM matters to you specifically: ASP.NET Core's generic host listens for it and runs IHostApplicationLifetime shutdown — draining requests, flushing logs, disposing DbContexts. kill -9 skips all of that. Same etiquette as "Close window" vs Task Manager's "End task".
BothKeep things running after you log out
$ dotnet OrderApi.dll &            # & = background job of THIS shell (dies with it)
$ jobs                              # list shell jobs; fg %1 brings one back
$ nohup dotnet OrderApi.dll > app.log 2>&1 &   # survives logout (quick & dirty)
$ tmux                              # better: a detachable terminal session
  inside tmux: run anything … then Ctrl+B, D to detach; later: tmux attach
tmux is the remote-desktop-session of the terminal world — your long task keeps running when Wi-Fi drops. For anything real, though, the correct answer is a systemd service (Concept 10), not nohup.
Deep dive: fork/exec, zombies and the OOM killer

Linux creates processes in two steps: fork() clones the current process, then exec() replaces the clone's program. When a child exits, it lingers as a zombie (STAT Z) until its parent reads the exit code — zombies hold no memory, but hundreds of them indicate a buggy parent that isn't reaping. You can't kill a zombie (it's already dead); restart the parent.

When RAM + swap run out, the kernel's OOM killer sacrifices the process with the worst score — frequently your JIT-heavy dotnet process. If your service vanished without an exception in its logs, check sudo dmesg | grep -i "out of memory" and journalctl -k. The fix is memory limits in the unit file (MemoryMax=) or right-sizing the VM.

.NET corner

Three openers for any misbehaving dotnet process: ls /proc/<pid>/fd | wc -l (open file/socket handles — leak detector), cat /proc/<pid>/limits (is it about to hit the open-files ceiling? Kestrel under load often does — raise via LimitNOFILE= in the unit), and dotnet-counters monitor -p <pid> (works identically on Linux). dotnet-dump collect -p <pid> gives you a core you can analyze back on Windows.

Concept 05

Stdin, stdout, stderr & pipes

Every process is born with three streams: stdin (fd 0), stdout (fd 1), stderr (fd 2). Pipes connect one program's stdout to the next one's stdin. This is the superpower of Linux: instead of one giant console app, you chain ten small ones. PowerShell borrowed the idea — but pipes objects; bash pipes text, so text-wrangling tools are the vocabulary.

Visual Guide: Streams Redirection & Pipes Pipeline

Redirection — six patterns cover 99% of use

BothThe redirection table, live
$ dotnet OrderApi.dll > out.log            # stdout → file (overwrite)
$ dotnet OrderApi.dll >> out.log           # stdout → file (append)
$ dotnet OrderApi.dll 2> err.log           # stderr only
$ dotnet OrderApi.dll > all.log 2>&1       # both streams, one file (order matters!)
$ dotnet ef database update < answers.txt  # file → stdin
$ noisy-tool 2>/dev/null                   # discard errors (/dev/null = NUL)
2>&1 reads "point stream 2 at wherever 1 currently points" — which is why it must come after > all.log. Exceptions and stack traces go to stderr, so if your captured log looks suspiciously clean, you forgot stream 2.
BothPipelines you'll actually run on day 3
$ journalctl -u orderapi --since "1 hour ago" | grep -i exception | tail -20
$ grep -c "HTTP/1.1\" 500" /var/log/nginx/access.log        # count 500s
$ awk '{print $9}' /var/log/nginx/access.log | sort | uniq -c | sort -rn
  # status-code histogram: awk grabs column 9, uniq -c counts, sort -rn ranks
$ ss -tn state established | wc -l                          # live TCP connections
$ dotnet OrderApi.dll 2>&1 | tee run.log                    # watch AND record
$ history | grep dnf                                        # what did I install last week?
The core vocabulary: grep (filter lines), awk (pick columns), sort, uniq -c (count duplicates), wc -l (count lines), tee (split the stream), head/tail (trim). Ten verbs, infinite sentences — the Unix grammar.
BothJSON logs? Meet jq
$ sudo dnf install -y jqsudo apt install -y jq
$ tail -200 /var/log/orderapi/app.json \
    | jq -r 'select(.Level=="Error") | "\(."@t") \(.RequestPath) \(.Exception)"'
If you use Serilog's compact JSON format, jq turns raw structured logs into queryable data right on the box — LINQ-for-the-terminal. select() is your Where(), the string template your Select().

Gotcha — pipes hide failures

In a pipeline, the exit code you see is the last command's. broken-cmd | tee log reports success because tee succeeded. In scripts, enable set -o pipefail (Concept 08) so a failure anywhere in the chain fails the pipeline — the difference between a deploy script that lies and one that doesn't.

.NET corner

Console apps on Linux should write logs to stdout/stderr and nothing else — systemd's journal (and Docker, and Kubernetes) captures the streams for you, timestamps them, and handles rotation. Drop file-logging gymnastics from your Linux deployments; Console + structured formatter is the native pattern, then read with journalctl -u orderapi.

Concept 06

Users, groups & sudo

root (UID 0) is the all-powerful account — Administrator without UAC's training wheels. Daily work happens as a normal user; sudo grants surgical, logged elevation per command. Users live in /etc/passwd, password hashes in /etc/shadow, groups in /etc/group — plain text files, true to form.

Identity and elevation

BothWho am I, and what may I do?
$ id
uid=1001(arun) gid=1001(arun) groups=1001(arun),10(wheel) ← Oracle  /  27(sudo) ← Ubuntu
$ sudo -l                      # list exactly what sudo allows me
$ sudo systemctl restart nginx # elevate ONE command (asks YOUR password)
$ sudo -i                      # full root shell — use sparingly, exit promptly
$ sudo -u orderapi whoami      # act as another user (test service perms)
The admin group differs by family: wheel on Oracle Linuxsudo on Ubuntu. Every sudo invocation is logged to /var/log/secure/var/log/auth.log — auditable elevation, unlike a perpetual admin session.
Oracle LinuxCreate an admin user
$ sudo useradd -m -s /bin/bash deploy     # -m = create /home/deploy
$ sudo passwd deploy                       # set password interactively
$ sudo usermod -aG wheel deploy            # -aG = APPEND to group (never forget -a!)
$ groups deploy                            # verify
RHEL family uses the low-level useradd; there is no friendly wrapper. Forgetting -a in usermod -G replaces all group memberships instead of adding — a classic lockout.
UbuntuCreate an admin user
$ sudo adduser deploy                      # friendly wizard: home, shell, password
$ sudo usermod -aG sudo deploy             # admin group is "sudo" here
$ groups deploy                            # verify
Debian family ships interactive adduser/deluser wrappers; the low-level useradd also exists. Group membership applies on next login — re-SSH before testing.
BothCreate a locked-down service account for your app
$ sudo useradd -r -s /usr/sbin/nologin -d /opt/orderapi orderapi
  -r          system account (low UID, no aging)
  nologin     nobody can SSH in as it
  -d          its "home" = the app directory
$ sudo chown -R orderapi:orderapi /opt/orderapi /var/log/orderapi /var/lib/orderapi
This is the Linux equivalent of running a Windows service as a virtual service account instead of LocalSystem. If the app is compromised, the blast radius is its own files — nothing else.
BothGrant precise sudo rights — visudo
$ sudo visudo -f /etc/sudoers.d/deploy     # NEVER edit /etc/sudoers directly
# allow deploy to manage only the orderapi service, no password:
deploy ALL=(root) NOPASSWD: /usr/bin/systemctl restart orderapi, /usr/bin/systemctl status orderapi
visudo syntax-checks before saving — a typo in sudoers can lock everyone out of elevation. Scoped rules like this are how CI/CD users restart services without holding root.

Concept 07

Package management

This is where the two families diverge the most — and where the header switch earns its keep. Ubuntu uses APT over .deb packages; Oracle Linux uses DNF (successor to yum) over .rpm. Same philosophy on both: signed repositories, automatic dependency resolution, one command to update the entire system — a world away from hunting installer EXEs.

Concept 08

Shell scripting anatomy

A bash script is just commands in a file, plus a shebang line telling the kernel which interpreter runs it. You write C#; you'll find bash crude but devastatingly effective for glue — deploys, health checks, log sweeps. Learn the anatomy and the three safety flags, and keep scripts under ~100 lines (beyond that, reach for a real language).

Anatomy, executed

BothA real deploy script — every construct labeled
#!/bin/bash                                # ① shebang: which interpreter
set -euo pipefail                          # ② safety: die on error/-u unset var/pipe fail

APP="orderapi"                             # ③ variables: NO spaces around =
RELEASE_DIR="/opt/${APP}/releases/$(date +%Y%m%d-%H%M%S)"   # $( ) = command substitution

if [[ ! -f "publish/${APP}.dll" ]]; then   # ④ conditional: [[ ]] for tests, -f = file exists
  echo "ERROR: run dotnet publish first" >&2
  exit 1                                   # ⑥ exit code: 0=success, non-zero=failure
fi

deploy() {                                 # ⑤ function
  sudo mkdir -p "$RELEASE_DIR"
  sudo cp -r publish/* "$RELEASE_DIR/"
  sudo chown -R "$APP:$APP" "$RELEASE_DIR"
  sudo ln -sfn "$RELEASE_DIR" "/opt/${APP}/current"    # atomic-ish switch
  sudo systemctl restart "$APP"
}

for f in publish/*.json; do                # ④ loop over a glob
  echo "shipping config: $f"
done

deploy
echo "deployed $APP → $RELEASE_DIR"
Save as deploy.sh, then chmod +x deploy.sh and run with ./deploy.sh. The ./ is required — unlike cmd.exe, Linux does not search the current directory for executables (a deliberate security choice).
BothThe idioms that prevent 2 a.m. incidents
$ echo $?                          # exit code of the last command (PowerShell's $LASTEXITCODE)
$ systemctl is-active orderapi && echo UP || echo DOWN   # && = on success, || = on failure
$ cp "$SRC" "$DST"                  # ALWAYS quote variables — spaces in paths break unquoted ones
$ VER="${1:?usage: deploy.sh <version>}"   # $1 = first argument, :? = require it
$ bash -n deploy.sh                 # syntax check without executing
$ bash -x deploy.sh                 # trace mode: echo every command as it runs
Install shellcheck (dnf install ShellCheckapt install shellcheck) and treat its output like compiler warnings — it catches quoting and logic bugs with Roslyn-analyzer-level precision.

Concept 09

Networking commands

For an app developer, networking on Linux boils down to four questions: what's my address, is my app listening, can I reach that endpoint, and is the firewall in the way? Four questions, four tools — plus the firewall layer, which is the second-biggest Oracle↔Ubuntu divergence after packages.

Visual Guide: Reverse Proxy Web Traffic Route

The four questions

Both① What's my address? — ip
$ ip addr            # interfaces + IPs (ipconfig /all)  — short: ip a
$ ip route           # routing table; first line = default gateway
$ ip -br addr        # -br = brief, the human-friendly view
ifconfig is deprecated; ip replaced it years ago. Interface names like ens160/eth0 are your "Ethernet adapter" equivalents; lo is loopback.
Both② Is my app listening? — ss
$ sudo ss -tulnp                       # Tcp+Udp, Listening, Numeric, Processes
tcp LISTEN 0 512  0.0.0.0:80     users:(("nginx",pid=812,…))
tcp LISTEN 0 512  127.0.0.1:5000 users:(("dotnet",pid=1973,…))  ← localhost only!
$ sudo ss -tulnp | grep 5000           # the daily one-liner
$ sudo lsof -i :5000                   # alternative: which process owns port 5000
Memorize ss -tulnp — it's netstat -ano + Task Manager's PID lookup in one. The bind address column is the big tell: 127.0.0.1:5000 is unreachable from outside the box; 0.0.0.0:5000 listens on all interfaces.
Both③ Can I reach it? — curl & friends
$ curl -i http://localhost:5000/health      # -i = include response headers
$ curl -s -o /dev/null -w "%{http_code} %{time_total}s\n" https://api.example.com
$ curl -X POST -H "Content-Type: application/json" -d '{"id":1}' http://localhost:5000/orders
$ ping -c 4 10.0.0.12                        # -c 4: Linux pings forever without it
$ dig api.example.com +short                 # DNS answer only (nslookup's better cousin)
$ traceroute api.example.com                 # the path (tracert)
$ nc -zv db-host 1521                        # "is THAT port open?" — Test-NetConnection
curl is Postman-in-the-terminal and lives on every server. The -w write-out format makes one-line health probes for scripts; nc -zv answers "firewall or app?" when a connection fails.
Oracle Linux④ Firewall — firewalld
$ sudo firewall-cmd --state
$ sudo firewall-cmd --list-all                       # current zone, open services/ports
$ sudo firewall-cmd --permanent --add-service=https  # open 443 by service name
$ sudo firewall-cmd --permanent --add-port=5000/tcp  # open a raw port
$ sudo firewall-cmd --reload                          # --permanent changes need a reload!
firewalld thinks in zones and services. The classic trap: forgetting --permanent (rule vanishes on reboot) or forgetting --reload (permanent rule isn't live yet). You usually need both forms of the same rule, or run with --permanent then reload.
Ubuntu④ Firewall — ufw
$ sudo ufw status verbose
$ sudo ufw allow OpenSSH            # FIRST, before enabling — or you lock yourself out
$ sudo ufw allow 443/tcp
$ sudo ufw allow from 10.0.0.0/24 to any port 5000 proto tcp   # scoped rule
$ sudo ufw enable
ufw (Uncomplicated Firewall) is exactly that — flat allow/deny rules, instantly persistent. Order of operations matters once in your life: allow SSH before ufw enable on a remote box.
Oracle LinuxThe hidden layer: SELinux
$ getenforce                          # Enforcing | Permissive | Disabled
$ sudo grep denied /var/log/audit/audit.log | tail   # what did it block?
# nginx reverse-proxying to Kestrel on 127.0.0.1:5000 gets blocked? Allow outbound:
$ sudo setsebool -P httpd_can_network_connect 1
# app listening on a non-standard port for a confined service:
$ sudo semanage port -a -t http_port_t -p tcp 5000
# files moved into web roots need correct labels:
$ sudo restorecon -Rv /opt/orderapi
SELinux is mandatory access control on top of file permissions — when "everything looks right but it still fails" on Oracle Linux, check here before anything else. Never disable it to "fix" an issue; sudo setenforce 0 (temporary permissive) is the honest diagnostic: if the problem vanishes, it's SELinux — re-enable with setenforce 1 and add the proper boolean/port/label. Ubuntu uses AppArmor instead, which seldom touches custom services.

Gotcha — "it works on the server but not from my laptop"

Debug in rings, inside-out: ① curl localhost:5000 on the box (app up?) → ② ss -tulnp (bound to 0.0.0.0 or only 127.0.0.1?) → ③ firewall rules (above) → ④ cloud security group / corporate network. .NET corner

Kestrel defaults to localhost:5000/5001 — fine behind a reverse proxy on the same box, invisible otherwise. Set ASPNETCORE_URLS=http://0.0.0.0:5000 (env or unit file) to expose it. Ports below 1024 are privileged: don't run dotnet as root for port 80 — either front it with nginx, or grant the one capability it needs: sudo setcap 'cap_net_bind_service=+ep' /opt/orderapi/OrderApi. Your MAUI / mobile clients hitting this API care about TLS — terminate HTTPS at nginx with a Let's Encrypt cert (certbot) and keep Kestrel on plain HTTP internally.

Concept 10

systemd & services

systemd is PID 1 — the init system that starts, supervises, and restarts everything. For you it's three things in one: the Services console (systemctl), Event Viewer (journalctl), and Task Scheduler (timers). This is the single most valuable concept for an app developer: it's how your code becomes a first-class citizen of the OS. Identical on Oracle Linux and Ubuntu.

Operating services

BothThe systemctl verbs
$ systemctl status nginx            # state, PID, recent log lines — the health card
$ sudo systemctl start nginx        # … stop | restart
$ sudo systemctl reload nginx       # re-read config without dropping connections
$ sudo systemctl enable --now nginx # start now AND on every boot — one command
$ systemctl is-active nginx; systemctl is-enabled nginx   # script-friendly checks
$ systemctl list-units --type=service --state=running
$ systemctl list-units --failed     # the morning-after triage view
enabled ≠ running: enabled means "starts at boot", active means "running now" — exactly Startup Type vs Status in services.msc. The web server unit is httpd on Oracle Linuxapache2 on Ubuntu if you use Apache; nginx is nginx everywhere.
Bothjournalctl — Event Viewer, but composable
$ journalctl -u orderapi -f                    # live tail of one service (THE command)
$ journalctl -u orderapi --since "30 min ago" -p warning   # by time + min priority
$ journalctl -u orderapi -b                     # since last boot
$ journalctl -u orderapi -o json | jq .MESSAGE | head      # structured output
$ journalctl --disk-usage && sudo journalctl --vacuum-size=500M   # tame journal growth
Everything a service prints to stdout/stderr lands here, timestamped and indexed — which is precisely why Concept 05 told you to log to the console.

Your .NET app as a real service — the full unit file

Both/etc/systemd/system/orderapi.service
[Unit]
Description=Order API (ASP.NET Core)
After=network.target                       # start after networking is up

[Service]
Type=notify                                # .NET 7+: add Microsoft.Extensions.Hosting.Systemd
                                           # + UseSystemd() — else use Type=simple
User=orderapi
Group=orderapi
WorkingDirectory=/opt/orderapi/current     # ← appsettings.json resolves from here!
ExecStart=/usr/bin/dotnet /opt/orderapi/current/OrderApi.dll
Environment=ASPNETCORE_ENVIRONMENT=Production
Environment=ASPNETCORE_URLS=http://0.0.0.0:5000
EnvironmentFile=-/etc/orderapi/orderapi.env   # secrets; "-" = optional if missing
Restart=always                             # supervise: resurrect on crash
RestartSec=5
KillSignal=SIGTERM                         # graceful: triggers IHostApplicationLifetime
TimeoutStopSec=30
LimitNOFILE=65536                          # Kestrel under load needs file descriptors
# hardening (optional but cheap):
NoNewPrivileges=true
ProtectSystem=strict
ReadWritePaths=/var/log/orderapi /var/lib/orderapi

[Install]
WantedBy=multi-user.target                 # "normal server boot" — see Concept 12
Activate it: sudo systemctl daemon-reload (re-read unit files — required after every edit) then sudo systemctl enable --now orderapi, verify with systemctl status orderapi and journalctl -u orderapi -f. This one file replaces a Windows Service wrapper, NSSM, and Recovery-tab settings combined.
Deep dive: timers — cron with logging and dependencies

Pair orderapi-cleanup.service (a oneshot unit running your cleanup command) with orderapi-cleanup.timer containing OnCalendar=*-*-* 02:30:00 and Persistent=true (catch up if the box was off). Enable the timer: sudo systemctl enable --now orderapi-cleanup.timer; inspect schedules with systemctl list-timers. Unlike cron you get journald logs, dependency ordering, and missed-run handling for free.

Gotcha — the daemon-reload ritual

Edited a unit file and the change "didn't take"? You skipped sudo systemctl daemon-reload. systemd caches unit definitions; reload re-parses them. Sequence to memorize: edit → daemon-reload → restart → status. .NET corner

Add the NuGet package Microsoft.Extensions.Hosting.Systemd and call .UseSystemd() on your host builder: with Type=notify systemd then knows the difference between "process launched" and "app actually ready", making systemctl start block until your health state is genuinely up — better zero-downtime restarts and accurate dependency ordering for free.

Concept 11

Disk & storage management

The chain is: physical disk → partitions → filesystem → mounted into the tree. Enterprise boxes add LVM (Logical Volume Manager) between partition and filesystem so volumes can grow without downtime — think Storage Spaces / dynamic disks, but standard and scriptable. Your two recurring real-world tasks: find what's eating space and grow a volume.

Task 1: the disk is full — find the eater

BothFrom symptom to culprit in four commands
$ df -h                                   # which filesystem is full?
/dev/mapper/ol-root   38G   36G  1.2G  97% /        ← this one
$ sudo du -xh / --max-depth=2 2>/dev/null | sort -rh | head -15
  # -x: stay on this filesystem (skip /proc etc.), sort by size, top 15
$ sudo du -sh /var/log/* | sort -rh | head # logs are the usual suspect
$ sudo journalctl --vacuum-size=300M       # shrink the journal
$ sudo lsof +L1 | head                      # deleted-but-open files still holding space
That last one solves a famous mystery: du says 20 GB used, df says 36 GB — a process holds a deleted log file open and the space won't free until it's restarted. Also check dnf clean allsudo apt clean (package caches) and docker system prune if containers live there.
Visual Guide: LVM Storage Layers & Mount Points

Task 2: grow a volume (the LVM chain)

BothSurvey the layers
$ lsblk                                    # the disk → partition → LV tree (start here, always)
sda             50G
├─sda1           1G  /boot
└─sda2          49G
  ├─vg0-root    30G  /
  └─vg0-data    19G  /var/lib/orderapi
$ sudo pvs && sudo vgs && sudo lvs         # physical volumes, volume groups, logical volumes
$ mount | grep vg0                          # what's mounted where, with which fs type
Read lsblk like a family tree: disks have partitions; partitions feed a volume group (the pool); logical volumes are carved from the pool and carry filesystems. PV/VG/LV → pvcreate, vgcreate, lvcreate when building from scratch.
Oracle LinuxGrow a volume — XFS (the OL default)
# after enlarging the cloud disk / adding capacity to the VG:
$ sudo lvextend -l +100%FREE /dev/vg0/data   # give the LV all free VG space
$ sudo xfs_growfs /var/lib/orderapi          # XFS grows by MOUNT POINT, online
$ df -h /var/lib/orderapi                    # verify
Oracle Linux defaults to XFS: grows online in seconds, but can never shrink — size conservatively and grow on demand. (lvextend -r runs the right grow tool for you on either filesystem.)
UbuntuGrow a volume — ext4 (the Ubuntu default)
# after enlarging the cloud disk / adding capacity to the VG:
$ sudo lvextend -l +100%FREE /dev/ubuntu-vg/ubuntu-lv
$ sudo resize2fs /dev/ubuntu-vg/ubuntu-lv    # ext4 grows by DEVICE, online
$ df -h /                                    # verify
# fresh Ubuntu installs often leave VG space unallocated on purpose — check vgs!
Ubuntu defaults to ext4 (resize2fs to grow; can also shrink, offline). The default LVM install frequently allocates only half the disk to / — "out of space" on a roomy disk usually means free extents are sitting in the VG waiting for exactly this command pair.
BothMount a new data disk permanently
$ lsblk                                     # identify the new disk, e.g. sdb
$ sudo mkfs.xfs /dev/sdb                    # or mkfs.ext4 — format it
$ sudo mkdir /data && sudo mount /dev/sdb /data
$ sudo blkid /dev/sdb                       # copy the UUID, then persist in /etc/fstab:
UUID=3f1c…  /data  xfs  defaults,nofail  0 2
$ sudo systemctl daemon-reload && sudo mount -a   # test fstab WITHOUT rebooting
Always mount by UUID (device names like sdb can shuffle between boots) and add nofail so a missing data disk doesn't stop the whole boot. mount -a is the safe dress rehearsal — a broken fstab discovered at boot time is a Concept-12 rescue session.

Concept 12

Linux boot process

Firmware (BIOS/UEFI) → GRUB bootloader → kernel + initramfs → systemd (PID 1) → target reached → login. Five stages, three to five seconds on a cloud VM. You need this concept for exactly two moments: when a server boots slowly, and when it doesn't boot at all.

Slow boot: profile it

Bothsystemd-analyze — the boot profiler
$ systemd-analyze                       # total: firmware / loader / kernel / userspace
$ systemd-analyze blame | head          # slowest units, ranked
$ systemd-analyze critical-chain        # the dependency path that gated boot
$ journalctl -b -p err                  # errors from THIS boot; -b -1 = previous boot
A unit "blamed" for 90 s is usually waiting on something — DNS, a dead NFS mount, a misordered dependency. critical-chain shows whether it actually delayed anyone else. journalctl -b -1 -e answers "why did it die last night?" after an unexpected reboot.

Targets — runlevels, modernized

BothWhat does this machine boot into?
$ systemctl get-default
multi-user.target          ← server: network + services, no GUI
$ sudo systemctl set-default multi-user.target   # graphical.target = with GUI
$ sudo systemctl isolate rescue.target            # drop to single-user maintenance NOW
This is why your unit file said WantedBy=multi-user.target (Concept 10): "when the machine reaches normal server mode, include me." The enable/disable mechanic is just symlinks into the target's .wants directory.

Kernel parameters & GRUB — the family split

Oracle LinuxChange kernel parameters
$ sudo grubby --info=DEFAULT                       # current default kernel + args
$ sudo grubby --update-kernel=ALL --args="audit=1" # add a parameter, all kernels
# the traditional route still works:
$ sudoedit /etc/default/grub
$ sudo grub2-mkconfig -o /boot/grub2/grub.cfg      # regenerate (note: grub2-*)
RHEL family prefers grubby with BLS (one snippet per kernel under /boot/loader/entries/) — it edits entries safely without regenerating the whole config. The kernel-switch trick from Concept 01 (UEK ↔ RHCK) is the same tool.
UbuntuChange kernel parameters
$ sudoedit /etc/default/grub
GRUB_CMDLINE_LINUX_DEFAULT="quiet splash audit=1"
$ sudo update-grub                                  # Ubuntu's wrapper for grub-mkconfig
$ reboot
$ cat /proc/cmdline                                 # verify what the kernel booted with
On Ubuntu it's always the same two-step: edit /etc/default/grub, run update-grub. Note the binary names differ across families: update-grub/grub-mkconfig here vs grub2-mkconfig there.
Deep dive: the won't-boot rescue playbook

At the GRUB menu (hold/press Shift or Esc early if hidden), press e on the entry and append to the linux line: systemd.unit=rescue.target (single-user with most services off) or systemd.unit=emergency.target (barest minimum, root fs read-only). Boot with Ctrl+X. Typical fixes from there: mount -o remount,rw /, repair a bad /etc/fstab line (the #1 cause — which is why Concept 11 insisted on nofail + mount -a), or disable the offending unit. Cloud VMs without console keyboards offer the same via their serial-console feature. The infographic's whiteboard wisdom applies: most cloud VMs boot in under 3 seconds — when one takes minutes, something specific is waiting, and blame/critical-chain will name it.

.NET corner

Boot order is your app's startup contract: After=network.target only waits for network management to be up, not actual connectivity — an API that needs DNS/DB at startup should either use After=network-online.target + Wants=network-online.target, or better, retry connections in code (Polly) so boot order stops mattering. Verify your service truly comes back from a cold start: sudo reboot, then systemctl status orderapi — the test most deployments skip until the first unplanned outage runs it for them.
