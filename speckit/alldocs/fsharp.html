Orientation

You know .NET. Now meet its best-kept secret.

F# is the functional-first language of .NET — same runtime, same BCL, same NuGet packages you already use, but with a type system that catches whole categories of bugs at compile time and a fraction of the ceremony. This manual walks you through the language hands-on, chapter by chapter, following Isaac Abraham's F# in Action. Every code card is real, runnable code — paste it into an .fsx script and run it interactively. Toggle the C# lens in the header to show or hide C# comparison callouts.

The five mental-model shifts

The friction for a C# developer isn't syntax — it's five assumptions that quietly stop being true:

  • Everything is an expression. if/else, match, even a code block — they all return a value. There are no statements that "do nothing and return void"; even side effects return unit.
  • Immutable by default. let x = 5 is final. Mutation requires opting in with mutable and the <- operator. You'll write 95% of code without it — and your code becomes trivially easy to reason about.
  • Types are inferred, not declared. The compiler works out types from usage — full static typing with the feel of a scripting language. You'll write int and string annotations rarely.
  • Data and behavior live apart. Instead of classes with methods, you model data with records and unions, then operate on it with standalone functions in modules. Think "C# static classes + immutable DTOs," minus the boilerplate.
  • Declaration order matters. Files compile top to bottom; a file can only see code declared above it. This sounds restrictive — it's actually F#'s secret weapon against spaghetti dependencies.

C# lens

The closest C# experience to FSI is LINQPad or dotnet-script / top-level programs — but FSI ships in the box and works with full type checking on every line you send. There is no "edit → rebuild → rerun the whole app" loop; you keep a live session and grow your program a few lines at a time. State stays in memory between evaluations.

Gotcha — whitespace is syntax

F# uses indentation instead of { }. The rule that covers 99% of cases: indent consistently with spaces (4 is standard), and anything indented under a let belongs to it. If FSI complains about "unexpected token" or "incomplete structured construct", check your indentation first. Tabs are a compile error.

Chapter 01

let, scoping & type inference

let binds a value to a symbol — that's it, and it replaces fields, locals, properties and methods in one keyword. Combined with the most powerful type inference on .NET, you get code that looks dynamic but is statically checked end to end.

let binds values — and functions are values

fsxOne keyword for everything
let isaac = 42                      // an int value
let fname = "Frank"                 // a string value
let fullName = $"{fname} Schmidt"   // computed from other values

// a function: same keyword, parameters after the name
let addTenThenDouble theNumber =
    let addedTen = theNumber + 10   // nested bindings, scoped to this function
    let answer = addedTen * 2
    printfn $"({theNumber} + 10) * 2 is {answer}"
    answer                          // last expression = return value

addTenThenDouble 5
val addTenThenDouble: theNumber: int -> int (5 + 10) * 2 is 30 val it: int = 30
Read the inferred signature int -> int as "takes an int, returns an int". The compiler worked that out because theNumber + 10 uses an int literal. No annotations anywhere — but this is fully statically typed; try addTenThenDouble "five" and you get a compile error, not a runtime crash.
fsxThe same function, fully annotated (you almost never do this)
let addTenThenDoubleVerbose (theNumber: int) : int =
    let addedTen: int = theNumber + 10
    let answer: int = addedTen * 2
    answer
Annotations go (name: Type) for parameters and : Type before the = for the return. You'll use them at public API boundaries, when inference needs a hint for .NET members (see below), or as documentation. Inside ordinary code, let the compiler do the work.
C# lens

var infers a local's type from its initializer and stops there. F# inference flows through entire call graphs: parameter types, return types, and generics are all solved together via Hindley–Milner inference. The C# equivalent of the snippet above needs a method signature like int AddTenThenDouble(int theNumber) — F# derives every part of it.

Scoping without braces

fsxIndentation creates scope — and lets you hide intermediate state
let greetingTextScoped =
    let fullName =
        let fname = "Frank"
        let sname = "Schmidt"
        $"{fname} {sname}"
    // fname / sname are out of scope here — only fullName survives
    $"Greetings, {fullName}"

// nested *functions* work the same way
let greetingFor person =
    let makeFullName fname sname = $"{fname} {sname}"
    let fullName = makeFullName "Frank" "Schmidt"
    $"Greetings {fullName} from {person}."
In C# you'd reach for a private helper method or pollute the method body with locals. Here you scope working data inside the value that needs it. The inner bindings are invisible outside, so refactoring is fearless — nothing else can depend on them.

Where inference shines — and where it needs help

fsxAutomatic generalization: you get generics for free
let combineElements a b c =
    let output = ResizeArray()    // .NET List<T> — T not yet known!
    output.Add a
    output.Add b
    output.Add c
    output

combineElements 1 2 3            // ResizeArray<int>
combineElements "a" "b" "c"      // ResizeArray<string>
val combineElements: a: 'a -> b: 'b -> c: 'c -> ResizeArray<'a> (constrained: 'a = 'b = 'c) val it: ResizeArray<int> = seq [1; 2; 3]
You wrote zero type parameters yet got a fully generic function — the compiler generalized it because nothing pinned the types down. ResizeArray is F#'s friendly alias for System.Collections.Generic.List<T>.
fsxThe one place inference gives up: .NET member access
// Won't compile: what type is theDate? AddDays exists on many types...
// let addThreeDays theDate = theDate.AddDays 3

// Fix: annotate the parameter
let addThreeDays (theDate: System.DateTime) = theDate.AddDays 3

// ...and now inference can ride along elsewhere:
let addAYearAndThreeDays theDate =
    let threeDaysForward = addThreeDays theDate   // theDate must be DateTime
    theDate.AddYears 1                            // so .AddYears now resolves!
Inference works left-to-right, top-to-bottom and can't guess which .NET type owns a "dot" member. Rule of thumb: when you dot into a parameter, annotate it — or arrange code so the compiler learns the type first, as in addAYearAndThreeDays.
Gotcha — shadowing, not assignment

Binding the same name twice (let x = 5 then let x = x + 1) is legal in scripts and nested scopes — but it's shadowing: a brand-new symbol hides the old one. It is not mutation. If two evaluations of the same FSI line behave oddly, you probably shadowed something. Chapter 02 covers real mutation.

Checkpoint
Why does let addThreeDays theDate = theDate.AddDays 3 fail to compile without an annotation?
Member ("dot") access is the main limit of F# type inference: many types could have an AddDays member, so you annotate the parameter — (theDate: System.DateTime) — and everything downstream is inferred again.
Chapter 02

Expressions, immutability & unit

C# is built on statements that do things; F# is built on expressions that produce things. Add immutable-by-default bindings and you get code where data flows visibly from input to output — no spooky action at a distance.

if/else returns a value

fsxBranches are expressions — both sides must produce the same type
let describeAge age =
    let ageDescription =
        if age < 18 then "Child"
        elif age < 65 then "Adult"
        else "OAP"
    let greeting = "Hello"
    $"{greeting}! You are a '{ageDescription}'."

describeAge 12
val describeAge: age: int -> string val it: string = "Hello! You are a 'Child'."
The whole if/elif/else evaluates to a string and is bound directly to ageDescription — like C#'s ternary ?:, but readable at any size. Because the branches must agree on type and an else is required (when the result isn't unit), you can't forget a case and accidentally return nothing.

unit: the type of "nothing useful"

fsxunit replaces void — and exposes hidden side effects
let printAddition a b =
    let answer = a + b
    printfn $"{a} plus {b} equals {answer}."   // printfn returns unit
    // no other final expression: this function returns unit

// DANGER: no parens = evaluated ONCE at binding time
let getTheCurrentTime = System.DateTime.Now      // a value, frozen
let rightNow () = System.DateTime.Now            // a function: unit -> DateTime

getTheCurrentTime = getTheCurrentTime   // always true — same frozen value
rightNow () = rightNow ()               // false (clock moved on)
val printAddition: a: int -> b: int -> unit val getTheCurrentTime: DateTime = 10/06/2026 14:03:11 val rightNow: unit -> DateTime
unit (written ()) is a real value meaning "nothing interesting". A function whose signature ends in -> unit is a red flag saying I exist only for side effects. And any function that takes unit as input — like rightNow () — must be getting its data from somewhere hidden (clock, disk, network). Signatures become an honesty report.
Gotcha — ignoring return values is explicit

In C# you can call a method and silently discard its result. F# warns you: if an expression mid-function returns a non-unit value you don't use, the compiler flags it. Discard deliberately with |> ignore — a built-in function that swallows any value and returns unit. That warning regularly catches real bugs ("I computed the new state… and threw it away").

Mutation is opt-in — and usually unnecessary

fsxListing 4.6 — a mutable gas tank, then the immutable refactor
// Opting in to mutation: 'mutable' keyword, '<-' to assign
let mutable gas = 100.0
let drive distance =
    if distance = "far" then gas <- gas / 2.0
    elif distance = "medium" then gas <- gas - 10.0
    else gas <- gas - 1.0

drive "far"; drive "medium"; drive "near"
gas   // 39.0 — but only if you ran the calls in exactly that order!

// The immutable version: state in, state out
let driveImmutable gas distance =
    if distance = "far" then gas / 2.0
    elif distance = "medium" then gas - 10.0
    else gas - 1.0

let initialState = 100.0
let firstState  = driveImmutable initialState "far"
let secondState = driveImmutable firstState "medium"
let finalState  = driveImmutable secondState "near"   // 39.0, provably
val mutable gas: float = 39.0 val driveImmutable: gas: float -> distance: string -> float val finalState: float = 39.0
The mutable version's behavior depends on hidden state and call order — the classic source of "works on my machine". The immutable version makes the data flow explicit: each call takes the previous state and returns the next. Same logic, but now it's repeatable, testable and thread-safe for free. In chapter 04 the pipeline operator turns that chain into one elegant line.
C# lens

C# has been drifting this way for years — readonly, record types, init-only setters, switch expressions — but they're all opt-in and the ecosystem defaults to mutability. F# flips every default: immutable, expression-based, non-null. You opt out when you have a measured reason (tight loops, interop), not opt in.

Try it — exercise 4.3

Rewrite driveImmutable so distance is an int: more than 50 halves the gas, more than 25 subtracts 10, more than 0 subtracts 1, otherwise gas is unchanged.

Show solution
fsxSolution
let drive43 gas distance =
    if distance > 50 then gas / 2.0
    elif distance > 25 then gas - 10.0
    elif distance > 0 then gas - 1.0
    else gas

Note the final else gas — every branch must return a value, so "no change" means returning the input untouched.

Checkpoint
A function has signature unit -> string. What does that tell you?
If a function needs no input but produces output, the data must come from somewhere hidden. F# signatures make impurity visible: unit on either side of the arrow is a side-effect tell.
Chapter 03

Shaping data: tuples & records

F# treats data modeling as a first-class activity. Tuples group values ad hoc; records give them names, structural equality and copy-update semantics — everything a C# DTO needs, in three lines, with zero boilerplate.

Tuples: lightweight grouping & deconstruction

fsxPack with a comma, unpack with a pattern
let theAuthor = "isaac", "abraham"          // string * string
let firstName, secondName = theAuthor       // deconstruct in one line

let nameAndAge = "Jane", "Smith", 25
let forename, surname, _ = nameAndAge       // _ discards what you don't need

// deconstruct directly in the parameter list:
let makeDoctor (_, sname) = "Dr", sname
makeDoctor theAuthor
val theAuthor: string * string = ("isaac", "abraham") val makeDoctor: 'a * string -> string * string val it: string * string = ("Dr", "abraham")
Type signatures write tuples as string * string. Use tuples for "two or three values traveling together for a moment" — returning multiple results, intermediate pairs. The moment the meaning of each slot isn't obvious, upgrade to a record.
fsxBonus: out-parameters become tuples
open System
let parsed, theDate = DateTime.TryParse "03 Dec 2020"
if parsed then printfn $"Day of week is {theDate.DayOfWeek}!"
Any .NET API with an out parameter — the whole TryParse family — is automatically exposed in F# as a tuple return. No out var dance.

Records: named, immutable, comparable

fsxDefine, create, copy-and-update, compare
type Address = {
    Line1: string
    Town: string
    Postcode: string
    Country: string
}

type Person = {
    Name: string * string     // fields can be tuples, records, anything
    Address: Address
}

let theAddress = {
    Line1 = "1 Main Street"
    Town = "London"
    Postcode = "SW1 1AA"
    Country = "UK"
}

// copy-and-update: a new record, sharing unchanged fields
let addressInDE = {
    theAddress with
        Town = "Berlin"
        Country = "DE"
}

// structural equality out of the box
let isaacOne = { Name = "Isaac", "Abraham"; Address = theAddress }
let isaacTwo = { Name = "Isaac", "Abraham"; Address = theAddress }
isaacOne = isaacTwo
val addressInDE: Address = { Line1 = "1 Main Street" Town = "Berlin" ... } val it: bool = true
Three big wins versus a C# class: (1) you must populate every field at creation — no half-initialized objects, ever; (2) with gives non-destructive updates; (3) = compares by value, deeply. The compiler infers which record type a { … } literal builds from its field names; disambiguate with { Person.Name = … } if two records share field names.
C# lens

C# 9 record types were directly inspired by this. Equivalent C#: public record Address(string Line1, string Town, string Postcode, string Country); plus with expressions. The F# versions predate them by a decade and remain stricter: no inheritance games, no mutable properties unless you ask, and exhaustive initialization is enforced at compile time rather than by nullable warnings.

Anonymous records: shapes on the fly

fsxFor one-off shapes — JSON payloads, projections, test data
let company = {|
    Name = "My Company Inc."
    Town = "The Town"
    Country = "UK"
    TaxNumber = 123456
|}

// extend on the fly — creates a *new, wider* anonymous type
let companyWithBankDetails = {|
    company with
        AccountNumber = 123
        SortCode = 456
|}

company.TaxNumber
val company: {| Country: string; Name: string; TaxNumber: int; Town: string |} val it: int = 123456
{| … |} needs no type declaration at all, yet stays fully typed — note the inferred signature. Perfect for LINQ-style projections (chapter 05) and quick JSON (chapter 10). Unlike C# anonymous types, they can be returned from functions and even extended with with.
Gotcha — field order in definitions vs creation

When creating a record you can list fields in any order, but you must supply all of them. If you see No assignment given for field 'X', you missed one — that's the point: adding a field to a record type instantly breaks every construction site until each one handles it. Cheap, compiler-enforced refactoring.

Write buildPerson taking (forename, surname, age) that returns a record with Name (full name string), Age, and Description ("child" under 18, else "adult").

The if/else sits directly in the field assignment — expressions everywhere.

Checkpoint
Two record values of the same type with identical field values are compared with =. The result is…
Records (and tuples, and the unions you'll meet in chapter 07) compare by value all the way down. This makes testing and caching dramatically simpler than reference equality.
Chapter 04

Functions, currying & the pipeline

Here's where F# clicks. Every function takes exactly one argument and returns one value — multi-argument functions are an illusion called currying. That illusion enables partial application, and partial application enables the operator you'll fall in love with: |>.

Currying & partial application

fsxListing 6.2 — supply some arguments now, the rest later
let add (firstNumber: int) (secondNumber: int) = firstNumber + secondNumber

let addFive = add 5        // partially applied: waiting for one more int
let fifteen = addFive 10   // 15

// real-world flavor: bake in configuration
type LetterType = Welcome = 0 | PaymentOverdue = 1
let sendEmailManyArgs sender letterType emailAddress postDate = ()
let sendOfficeWelcome = sendEmailManyArgs "office@firm.com" LetterType.Welcome
sendOfficeWelcome "fred@email.com" System.DateTime.UtcNow
sendOfficeWelcome "joanne@email.com" (System.DateTime.UtcNow.AddDays 1.)
val add: firstNumber: int -> secondNumber: int -> int val addFive: (int -> int) val fifteen: int = 15
Now the arrows in int -> int -> int make sense: add takes an int and returns a function int -> int. Stop anywhere along the chain and you've created a specialized function — dependency injection without containers, configuration without builder classes.

The pipeline operator

fsxListings 6.3–6.5 — from inside-out nesting to top-down flow
let multiply (a: int) (b: int) = a * b

// Without pipelines: temp variables, or unreadable inside-out nesting
let finalValueChained = multiply (add (add 5 10) 7) 2

// With |>: data flows left to right
let pipelineCalc = 10 |> add 5 |> add 7 |> multiply 2   // 44

// This is how real F# programs read (stubs omitted — Listing 6.5):
customerId
|> loadFromDb
|> reviewCustomer
|> createEmail EmailTemplate.Overdue
|> send
val pipelineCalc: int = 44
x |> f simply means f x — pass the left side as the last argument of the right side. It works precisely because of currying: add 5 is already a one-argument function waiting for the piped value. Reading top to bottom you see load → review → create → send: the business process is the code.
C# lens

You already love this style — it's LINQ method chains and fluent builders. The difference: chaining in C# requires the API author to design a fluent interface (returning this, extension methods). |> works with every function ever written, including yours from five minutes ago, because it's just function application.

Organizing code: namespaces & modules

fsxModules are static classes that hold values, functions and types
module FsInAction.MyMaths

let add x y = x + y
let subtract x y = x - y

// nested module for the heavy machinery
module Complicated =
    let ten = 10
    let addTogetherThenSubtractTen x y = add x y |> subtract ten

// elsewhere:  open FsInAction.MyMaths
//             Complicated.addTogetherThenSubtractTen 4 5
A module compiles to a static class; open is using static. The idiomatic layout: a type Customer = … record, then a module Customer next to it containing every function operating on customers — data and behavior adjacent but separate. Remember file order matters: in an .fsproj, Domain.fs must sit above the files that use it.
Gotcha — parentheses are for grouping, not calling

sendOfficeWelcome "joanne@email.com" (DateTime.UtcNow.AddDays 1.) — those parens don't "call with arguments", they group the inner expression so it's evaluated first. Without them, F# would read DateTime.UtcNow.AddDays and 1. as two separate arguments. If you get a baffling type error with multiple arguments, look for a missing grouping paren first.

Try it — exercise 6.2

Take the drive function from chapter 02 (int distances). Reorder its parameters so it pipelines naturally, then drive three legs — 55, 26, 1 — starting from 100.0 gas, in a single pipeline.

Show solution
fsxSolution

    if distance > 50 then gas / 2.0
    elif distance > 25 then gas - 10.0
    elif distance > 0 then gas - 1.0

Parameter order is API design in F#: the "data" parameter goes last so partial application leaves a pipeline-ready function. Every List.map-style function in the standard library follows this convention.

Checkpoint
What does 10 |> add 5 literally evaluate?
x |> f = f x. Since add 5 is a partially-applied function of one int, 10 |> add 5 is (add 5) 10 = add 5 10 = 15.
Chapter 05

Collections: where pipelines pay rent

F#'s collection modules are LINQ with the volume turned up: more combinators, immutable by default, and designed for the pipeline. This is the chapter where a page of imperative loops collapses into four honest lines.

The motivating refactor — Listing 7.2 vs 7.3

fsxWhich team won the most away games?
type Result = { HomeTeam: string; HomeGoals: int; AwayTeam: string; AwayGoals: int }
let create home hg away ag = { HomeTeam = home; HomeGoals = hg; AwayTeam = away; AwayGoals = ag }

let results = [
    create "Messiville" 1 "Ronaldo City" 2
    create "Messiville" 1 "Bale Town" 3
    create "Ronaldo City" 2 "Bale Town" 3
    create "Bale Town" 2 "Messiville" 1
]

// The imperative version (Listing 7.2) needs ~15 lines: a mutable
// ResizeArray, nested for-loops, a found flag, and a mutable "best so far".

// The functional version:
let isAwayWin result = result.AwayGoals > result.HomeGoals

let wonAwayTheMost =
    results
    |> List.filter isAwayWin
    |> List.countBy (fun result -> result.AwayTeam)
    |> List.maxBy (fun (team, count) -> count)
val wonAwayTheMost: string * int = ("Bale Town", 2)
Filter the away wins, count occurrences per team, take the max by count. Each step is independently testable, there's no mutable state to corrupt, and the code reads like the requirement. countBy and maxBy have no direct LINQ equivalents — F# ships ~200 of these combinators.

fsxSlicing, dictionaries, maps and sets — Listings 7.4–7.9
let numbers = [ 1..10 ]

// immutable Map vs read-only dictionary
let data = [ "Isaac", "F#"; "Fred", "C#"; "Sam", "F#"; "Jo", "PHP" ]

let salesWithoutBonuses = salesEmployees - bonusEmployees
val salesWithoutBonuses: Set<Employee> = set [{ Name = "Brian" }]
Note - on sets — set difference as an operator. And because records have structural equality (chapter 03), sets and maps of records "just work" without writing IEqualityComparer.

fold: the aggregation primitive

fsxEvery loop-with-accumulator is a fold
// imperative sum
let sum inputs =
    let mutable accumulator = 0
    for input in inputs do
        accumulator <- accumulator + input
    accumulator

// the same shape, captured as a function
let sumFunctional inputs =
    inputs |> Seq.fold (fun accumulator input -> accumulator + input) 0

sumFunctional [ 1..5 ]   // 15: 0+1 → 1+2 → 3+3 → 6+4 → 10+5
val sumFunctional: inputs: int seq -> int val it: int = 15
fold takes a folder function (state, item) → newState and a starting state. sum, max, countBy — all folds in a costume. You'll rarely call fold directly (a named combinator usually exists) but recognizing the pattern unlocks reading any F# codebase.
Gotcha — seq is lazy, and re-runs every time

A seq pipeline does nothing until enumerated — and re-executes on every enumeration. If you iterate an expensive Seq.map twice, you compute twice. Materialize with Seq.toList / Seq.toArray once you're done transforming. Lists and arrays are eager; this trap is seq-only.

C# lens

Mapping table: Select → map, Where → filter, SelectMany → collect, Aggregate → fold, GroupBy → groupBy, OrderBy → sortBy, First → head, FirstOrDefault → tryHead (returns an Option — no nulls!). Each exists in List, Array and Seq flavors that preserve the collection type.

Chapter 06

Pattern matching: switch with a brain

match looks like C#'s switch expression, but it deconstructs data while it tests, nests arbitrarily deep, and — crucially — the compiler proves you handled every case. Forgotten branches become warnings at compile time, not bugs at 3 a.m.

Match on values, tuples, and shapes

fsxListing 8.2 — collapsing a truth table
// (yearsAsCustomer, hasOverdraft) → may they take out a loan?
let customerDetails = 2, true

// every combination spelled out…
let canTakeOutALoan =
    match customerDetails with
    | 0, true -> false
    | 0, false -> false
    | 1, true -> false
    | 1, false -> true
    | _ -> true

// …then simplified with wildcards and OR-patterns:
let canTakeOutALoanV4 =
    match customerDetails with
    | 0, _
    | 1, true -> false
    | _ -> true
val canTakeOutALoanV4: bool = true
Patterns are checked top to bottom; first match wins. _ is "anything", and stacking patterns above a single arrow (| A | B -> …) OR-combines them. The compiler warns on both unreachable rules and missing cases — try deleting the final | _ and watch it tell you exactly which inputs are unhandled.

Matching records, with guards, recursively

fsxListings 8.3–8.6 — fields, when-guards, nested records
type OverdraftDetails = { Approved: bool; MaxAmount: decimal; CurrentAmount: decimal }
type CustomerWithOverdraft = { YearsOfHistory: int; Overdraft: OverdraftDetails; Country: string }

let canApprove customer =
    match customer with
    | { YearsOfHistory = 0; Overdraft = { Approved = true } } -> true
    | { YearsOfHistory = 0 } -> false
    | { YearsOfHistory = 1; Overdraft = { Approved = true } } -> true
    | { YearsOfHistory = 1 } -> false
    | _ -> true

// 'when' guards for arbitrary logic, 'as'/binding to capture values
let bindingExample customer =
    match customer with
    | { Overdraft = { Approved = true; CurrentAmount = amount } } ->
        printfn $"Approved; current overdraft is {amount}"
    | { Overdraft = { Approved = false } as details } when customer.YearsOfHistory > 1 ->
        printfn $"Long history but unapproved overdraft: {details}"
    | _ -> printfn "Declined"
Record patterns drill into nested structures in one visual shape — no customer.Overdraft.Approved && … chains. Bind values mid-pattern (CurrentAmount = amount), capture a whole matched part (as details), and add when guards for what patterns can't express. One warning: guards reduce the compiler's exhaustiveness checking, so prefer plain patterns when possible.

Matching lists

fsxCollection patterns — heads, tails, exact shapes
type LoanRequest = {
    YearsOfHistory: int
    HasOverdraft: bool
    IsLargeRequest: bool
}

let summariseLoanRequests requests =
    match requests with
    | [] -> "No requests made!"
    | [ { IsLargeRequest = true } ] -> "Single large request!"

    | _ -> "Anything else"
[] matches empty, [ a; b ] matches exactly-two, and head :: rest splits a list like the 50-year-old Lisp idiom it is — while simultaneously pattern-matching into the records inside. This is why List is the default F# collection: it pattern-matches; arrays and seqs mostly don't.
C# lens

C# 8+ has been importing this feature wholesale: switch expressions, property patterns ({ Length: > 0 }), positional and list patterns. The remaining gaps: C# exhaustiveness checking is best-effort (you still need a discard arm to compile), and C# can't match into the discriminated unions you'll meet next chapter — which is where pattern matching goes from convenient to transformative.

Gotcha — don't match booleans

match x with | true -> … | false -> … compiles fine but is just a noisy if/else. Use match when there's structure to deconstruct or 3+ cases; use if/then/else for simple booleans. Idiomatic F# uses both.

Chapter 07

Discriminated unions: F#'s superpower

Records are "this AND that". Discriminated unions (DUs) are "this OR that" — a closed set of named cases, each carrying its own data. Combined with pattern matching, they let you make illegal states unrepresentable. This is the single feature C# developers miss most after learning F#.

Defining and consuming a DU

fsxListings 8.8–8.9 — a contact method is exactly one of three things
type ContactMethod =
    | Email of address: string
    | Telephone of country: string * number: string
    | Post of {| Line1: string; City: string; Country: string |}

let isaacEmail = Email "isaac@myemailaddress.com"
let isaacPhone = Telephone ("UK", "020-8123-4567")

let describe contactMethod message =
    match contactMethod with
    | Email address -> $"Emailing '{message}' to {address}."
    | Telephone (country, number) -> $"Calling {country}-{number}: '{message}'!"
    | Post details -> $"Posting '{message}' to {details.Line1}, {details.City}…"

describe isaacPhone "DUs FTW"
val it: string = "Calling UK-020-8123-4567: 'DUs FTW'!"
Each case has a name and its own payload shape — an email is a string, a phone number is two, a letter is an address record. Matching deconstructs the payload in the same gesture. Now add a case — | Sms of TelephoneNumber — and the compiler warns on every match in the codebase that doesn't handle it. That's exhaustive domain evolution, for free.
C# lens

The C# encoding of this is an abstract class with three subclasses, or an enum plus nullable fields that only sometimes apply — both let illegal states exist (what does EmailAddress mean when Kind == Telephone?). DUs are closed: no one can add a sneaky fourth subclass in another assembly, which is exactly what makes exhaustive matching sound. (C# union types remain a perennially-discussed proposal.)

Single-case DUs: types instead of stringly-typed chaos

fsxListing 8.11 — wrap your primitives
type PhoneNumber = PhoneNumber of string

    | Local of PhoneNumber
    | International of CountryCode * PhoneNumber

// unwrap by pattern matching — even directly in a parameter:

// enforce invariants with a validation pipeline:

    else failwith "Invalid email"

Modeling with the full toolkit

Chapter 08

Options & Results: the end of null

F# types declared in F# can't be null. "Might be missing" becomes Option<'T>; "might fail, and here's why" becomes Result<'T,'Error>. Both are plain DUs from the previous chapter — the magic is that the compiler forces every caller to handle both branches.

Option: Some or None, no third state

fsxAbsence you cannot forget to check
let optionalNumber: int option = Some 10
let missingNumber: int option = None

// missingNumber + 5         // ✗ compile error — it's not an int!
// missingNumber.CompareTo 55 // ✗ no such member on option

let description =
    match optionalNumber with
    | Some number -> $"The number is {number}"
    | None -> "There is no number"

// transform without unwrapping: Option.map
let tryGetFileContents filename =
    if System.IO.File.Exists filename then Some (System.IO.File.ReadAllText filename)
    else None

let countWords (text: string) = text.Split ' ' |> Array.length

let countWordsInFile filename =
    filename |> tryGetFileContents |> Option.map countWords
    // Some text → Some count;  None → None, countWords never runs
val countWordsInFile: filename: string -> int option
An int option is a different type from int — you physically cannot use it as a number until you pattern match (or map) it. Option.map applies a function inside the box: the happy path composes cleanly, and None short-circuits through the whole pipeline. Option.bind is the same but for functions that themselves return options — it flattens option option nesting.
C# lens

Nullable reference types (string?) were C#'s answer — but they're advisory warnings layered over a runtime where null still flows everywhere. Option is enforced: there is no .Value-without-checking that sneaks past the compiler in idiomatic code. For interop, F# gives you Option.ofObj (null → None) and Option.ofNullable at the boundary — convert once at the edges, then nulls don't exist inside your domain.

Result: errors as data

fsxListing 9.2 — validation that returns instead of throws
type CustomerId = CustomerId of int
type Country = Domestic | Foreign of string

let validateCustomerId (raw: string) =
    if raw.StartsWith "C" then Ok (CustomerId (int raw[1..]))
    else Error $"Invalid Customer Id '{raw}'."

let validateCountry raw =
    match raw with
    | "" -> Error "No country supplied"
    | "USA" -> Ok Domestic
    | other -> Ok (Foreign other)

// combine: only build the customer if BOTH succeeded
let validateCustomer rawId rawCountry =
    match validateCustomerId rawId, validateCountry rawCountry with
    | Ok customerId, Ok country -> Ok {| Id = customerId; Country = country |}
    | Error err, _ | _, Error err -> Error err

validateCustomer "C123" "USA"
validateCustomer "123" "USA"
val it: Result<{| Country: Country; Id: CustomerId |}, string> = Ok { Country = Domestic; Id = CustomerId 123 } val it: ... = Error "Invalid Customer Id '123'."
Result<'T,'Error> is just Ok of 'T | Error of 'Error. Failure is in the signature, so callers must decide what an error means at the call site — no invisible exception paths, no catch (Exception) guessing games. Matching the two results as a tuple is the manual way to combine validations; chapter 09 automates it.
fsxLevel up: strongly-typed errors + exceptions at the boundary
// errors as a DU — callers can match on the KIND of failure
type CustomerValidationError =
    | InvalidCustomerId of string
    | InvalidCountry of string

// wrap exception-throwing .NET code into Results at the edge:
let handleException func arg =
    try func arg |> Ok
    with ex -> Error ex

let divide (a, b) = a / b
let divideSafe = handleException divide
divideSafe (2, 0)
val divideSafe: (int * int -> Result<int, exn>) val it: Result<int, exn> = Error System.DivideByZeroException: …
Rule of thumb from the book: use Result for failures you expect and want callers to reason about (validation, lookups, business rules); let exceptions handle the truly exceptional (disk died, network gone) and convert at boundaries. Note how handleException is a higher-order function that makes any unsafe function safe.
Gotcha — don't reach for .Value

Option.get, .Value and friends unwrap without checking and throw on None — they reintroduce the NullReferenceException with extra steps. If you "know" it's Some, encode why with a match and a meaningful error. In tests, fine; in domain code, treat .Value as a code smell.

Checkpoint
When should you prefer Result over throwing an exception?
Results put expected failure into the type signature, forcing explicit handling. Exceptions stay the right tool for unexpected, unrecoverable situations — and you convert between worlds at the boundary with helpers like handleException.
Chapter 09

Computation expressions: taming the boxes

Once everything returns Options and Results, combining them gets noisy — match inside match inside match. Computation expressions (CEs) flatten that nesting: let! unwraps a boxed value or exits early, automatically. You've used this before — it's await, generalized to any container.

The problem, then the cure

fsxListing 9.6 — combining three parses, manually vs with option { }
open System
let calc (a: int) (b: int) (c: int) : int = a + b * c

let tryParseNumber (s: string) =
    match Int32.TryParse s with
    | true, number -> Some number
    | false, _ -> None

// manual combination — already clumsy with 3, unbearable with 5:
let calcResult =
    match tryParseNumber "1", tryParseNumber "2", tryParseNumber "3" with
    | Some a, Some b, Some c -> Some (calc a b c)
    | _ -> None

// the computation expression version:
#r "nuget: FsToolkit.ErrorHandling"
open FsToolkit.ErrorHandling

let myMaybeData = option {
    let! numberOne   = tryParseNumber "1"
    let! numberTwo   = tryParseNumber "2"
    let! numberThree = tryParseNumber "3"
    return calc numberOne numberTwo numberThree
}
val myMaybeData: int option = Some 7
Inside option { }, let! means "unwrap the Some, or if it's None, stop here and return None". The early-exit plumbing you'd write by hand is generated by the builder. return wraps the final value back into the container. Change "2" to "two" and the whole block evaluates to None — no exceptions, no nesting. The #r "nuget:…" line pulls a NuGet package straight into a script.

result { } and validation { } — fail fast vs collect-all

fsxExercise 9.2 — accumulate every validation error with and!
// result { } short-circuits on the FIRST Error.
// validation { } with and! runs ALL checks and collects every Error:

let validateCustomerCe rawId rawCountry rawName = validation {
    let! customerId = validateCustomerId rawId
    and! country    = validateCountry rawCountry
    and! name       = validateName rawName
    return {| Id = customerId; Country = country; Name = name |}
}

validateCustomerCe "123" "" "Isaac the Great Abraham"
// Error [ InvalidIdFormat "123"; NoCountrySupplied; TooManyParts ]
let! … and! … declares the steps as independent, so the builder can evaluate all of them and merge failures — exactly what a web form needs ("here are all 3 problems", not one-at-a-time). The same body with let! everywhere would stop at the first error. One keyword changes the strategy; the business code is untouched.
C# lens

async/await is a computation expression that C# hard-wired for exactly one container (Task). LINQ query syntax is another, hard-wired for IEnumerable. F# exposes the mechanism: option { }, result { }, task { } (chapter 12), seq { }, and ones you define yourself. Same let! keyword, different "awaitable" semantics per builder.

Gotcha — know your keywords

Inside a CE: let! unwraps a container; plain let binds a normal value (no unwrapping); return wraps a value into the container; return! passes an already-wrapped value through; do! is let! for unit-returning operations. Mixing up let and let! is the #1 beginner CE error — the compiler message will mention unexpected 'a option-style types.

Checkpoint
In option { let! x = f () … }, what happens when f () returns None?
That early exit is the whole point: let! encodes "unwrap or bail" so the happy path reads linearly while the failure path is handled by the builder.
Chapter 10

Working with data: JSON & type providers

Real systems live on messy external data. The F# pattern: deserialize into a dumb "raw" type, then validate into your rich domain with Results. And for exploration, type providers generate types from live data sources at edit time — IntelliSense against a JSON file or a Wikipedia page.

The two-stage deserialization pattern

fsxListing 10.3 — raw type in, validated domain out
open System.Text.Json
#r "nuget: FsToolkit.ErrorHandling"
open FsToolkit.ErrorHandling

// 1. a dumb shape that matches the JSON exactly
type RawGuitar = { Brand: string; Strings: string; Pickups: string list }

// 2. elevate it into the rich domain from chapter 07
let tryAsFullGuitar (raw: RawGuitar) = result {
    let! brand =
        if System.String.IsNullOrWhiteSpace raw.Brand then Error "Brand is mandatory"
        else Ok (Brand raw.Brand)

    let! strings =
        match raw.Strings with
        | "6" -> Ok Six | "7" -> Ok Seven | "8" -> Ok Eight | "12" -> Ok Twelve
        | value -> Error $"Invalid value '{value}'"

    let! pickups =
        raw.Pickups
        |> List.traverseResultM (fun p ->
            match p with
            | "S" -> Ok Pickup.Single
            | "H" -> Ok Pickup.Humbucker
            | value -> Error $"Invalid value {value}")

    return {
        Brand = brand
        Strings = strings
        Kind = match pickups with [] -> Acoustic | pickups -> Electric pickups
    }
}

"""{ "Brand": "Ibanez", "Strings": "6", "Pickups": [ "H", "S", "H" ] }"""
|> JsonSerializer.Deserialize
|> tryAsFullGuitar
val it: Result<Guitar, string> = Ok { Brand = Brand "Ibanez" Strings = Six Kind = Electric [Humbucker; Single; Humbucker] }
Serializers and rich F# types (DUs, single-case wrappers) don't mix well — so don't fight it. Deserialize into primitives, then run one honest validation pass that returns Result. traverseResultM turns a list of results into a result of list — "all pickups valid, or the first error". Bonus: serializing out is easy — project into an anonymous record and JsonSerializer.Serialize it.

C# lens

Checkpoint
Why deserialize into a "raw" record before building your domain type?
JSON is stringly-typed; your domain isn't. The raw type absorbs the mess 1:1, then one function — returning Result — owns the translation. Invalid data can't leak past it.

C# interop: one runtime, two dialects

One rule has no workaround: a single project is one language — you mix at assembly granularity, and your .sln happily holds both. C# sees an F# record as a sealed class with a constructor, IEquatable, and readonly properties.

Gotcha — F# functions are not .NET delegates

An F# lambda is an FSharpFunc, not a Func<,>/Action. Passing lambdas to C# APIs usually converts automatically, but when overload resolution gets confused, construct explicitly: System.Func<_,_>(fun x -> …). Symmetrically, C# devs calling your F# get a nicer time if public APIs take BCL delegate types.

Checkpoint
What's the idiomatic F# tool for a one-off ILogger stub in a test?
Object expressions implement interfaces inline with zero ceremony, which removes most of the need for mocking libraries in F# test suites (chapter 14 pushes this further with plain function injection).
Chapter 12

Async & tasks: await, the F# way

Asynchrony in F# is the task { } computation expression — same TPL machinery as C#, same performance, but let! instead of await. If you know async/await, you already know 90% of this chapter; the rest is composing tasks with collections and Results.

task { } basics

fsxListing 12.1 — let! is await, do! is await-for-unit
open System.IO
open System.Threading.Tasks

let writeToFileAsync fileName data = task {
    do! File.AppendAllTextAsync (fileName, data)     // await a Task (no result)
    let! contents = File.ReadAllTextAsync fileName   // await a Task<string>
    return contents.Length                           // → Task<int>
}

let totalTask = writeToFileAsync "sample.txt" "foo"
totalTask.Result   // blocking .Result is fine in FSI / scripts only!
val writeToFileAsync: fileName: string -> data: string -> Task<int> val it: int = 3
Mapping: task { } opens an async method body, let! = await with a result, do! = await without one, return sets the task's value. The function's inferred type is an honest Task<int> — directly consumable from C#, ASP.NET, anywhere.

Sequential vs parallel composition

fsxListings 12.2–12.3 — three files, two strategies
// sequential: each let! awaits before the next starts
let filesComposed = task {
    let! file1 = File.ReadAllTextAsync "file1.txt"
    let! file2 = File.ReadAllTextAsync "file2.txt"
    let! file3 = File.ReadAllTextAsync "file3.txt"
    return $"{file1} {file2} {file3}"
}

// parallel: kick all off, await them together
let filesParallel = task {
    let! allFiles =
        [ "file1.txt"; "file2.txt"; "file3.txt" ]
        |> List.map File.ReadAllTextAsync     // a list of running Task<string>
        |> Task.WhenAll                       // → Task<string[]>
    return allFiles |> Array.reduce (sprintf "%s %s")
}
The parallel version is a pipeline: map the file names into already-started tasks, then Task.WhenAll gathers them. Collections + tasks compose with the same combinators you learned in chapter 05 — no Select(async x => …) contortions.
fsxListing 12.7 — tasks + Results: the full honesty stack
open System.Text.Json
let loadCustomerFromDbAsync customerId = task { return {| Name = "Isaac"; Balance = 0 |} }

let tryGetCustomerAsync customerId = task {
    let! customer = loadCustomerFromDbAsync customerId
    return
        if customer.Balance <= 0 then Error "Customer is in debt!"
        else Ok customer
}

let handleRequestAsync (json: string) = task {
    let request: {| CustomerId: int |} = JsonSerializer.Deserialize json
    let! response = tryGetCustomerAsync request.CustomerId
    return
        match response with
        | Ok c -> {| CustomerName = c.Name.ToUpper() |}
        | Error msg -> failwith $"Bad request: {msg}"
}
Signature: Task<Result<Customer, string>> — "this is slow, AND it can fail, and here's how". Awaiting unwraps the task layer; matching unwraps the result layer. When the double-unwrapping gets tedious, FsToolkit.ErrorHandling's taskResult { } CE unwraps both in one let! — you'll see it in the Giraffe chapter next.
C# lens

F# also has an older async { } block (it pioneered async — C# borrowed the idea for await). Differences: F# async is cold (a recipe that runs when you ask, composable and restartable) whereas Task is hot (already running when created). For mainstream .NET work, the book's advice is simple: default to task { } — it's faster with Task-based APIs and frictionless with the ecosystem. Reach for async when you need cold semantics; bridge with Async.AwaitTask.

Gotcha — code before the task block runs synchronously

In Listing 12.4 the book shows a function that prints, blocks a second, then opens task { }: everything before the block executes synchronously on the caller's thread when the function is called. Same rule as C# async methods before the first await — keep slow synchronous work out of async functions' preambles.

Checkpoint
Inside task { }, what's the difference between let! and do!?
Both await. let! x = … is var x = await …; do! … is await …; for unit/void-style tasks, like Task.Delay or appending to a file.
Chapter 13

Web apps with Giraffe

Giraffe is a thin functional layer over ASP.NET Core: same Kestrel, same middleware, same performance — but your endpoints are functions composed with combinators instead of attribute-decorated controller classes. A whole API becomes one readable expression.

HttpHandler: the one abstraction

TerminalBootstrap a Giraffe app
$ dotnet new console -lang F# -o MyGiraffeApp && cd MyGiraffeApp
$ dotnet add package Giraffe
$ dotnet add package FsToolkit.ErrorHandling.TaskResult
$ dotnet run     # http://localhost:5000
No template magic required — a Giraffe app is a console app with a package reference and ~6 lines of bootstrap (below).
Program.fsListings 13.4–13.5 — compose routes with >=> and choose
open Microsoft.AspNetCore.Builder
open Giraffe

// the simplest possible handler:
let giraffeApp: HttpHandler = text "Hello, world!"

// combinators chain with the "fish" operator >=> …
let appV2: HttpHandler =
    GET >=> route "/device/status" >=> text "device is operating correctly"

// …and choose [] tries handlers top to bottom until one responds:
let fullApi: HttpHandler =
    choose [
        GET  >=> route "/device/status"  >=> text "device is operating correctly"
        POST >=> route "/device/execute" >=> text "executed a command!"
    ]

let builder = WebApplication.CreateBuilder()
builder.Services.AddGiraffe() |> ignore
let app = builder.Build()
app.UseGiraffe fullApi
app.Run()
An HttpHandler is (conceptually) HttpContext → maybe a response. GET, route, text, json are all just handlers; >=> glues them ("if this succeeds, continue to that"), choose is routing. Your entire URL space is one expression you can read top to bottom — no attribute scanning, no reflection magic.

Real handlers: query strings, JSON bodies, validation

Program.fsListings 13.6–13.7 — a validated endpoint with taskResult
open Microsoft.AspNetCore.Http
open FsToolkit.ErrorHandling

type DeviceStatusError =
    | NoDeviceIdSupplied
    | InvalidDeviceId of string
    | NoSuchDeviceId of int

module Db =
    let tryFindDeviceStatus (deviceId: int) = task {
        if deviceId < 50 then return Some "ACTIVE"
        elif deviceId < 100 then return Some "IDLE"
        else return None
    }

// async + validation in one readable block (chapter 12's promise!)
let tryGetDeviceStatus maybeDeviceId = taskResult {
    let! (rawId: string) = maybeDeviceId |> Result.requireSome NoDeviceIdSupplied
    let! deviceId = Option.tryParse rawId |> Result.requireSome (InvalidDeviceId rawId)
    let! status = Db.tryFindDeviceStatus deviceId
    let! status = status |> Result.requireSome (NoSuchDeviceId deviceId)
    return {| DeviceId = deviceId; Status = status |}
}

let warehouseApi next (ctx: HttpContext) = task {
    let! deviceStatus = tryGetDeviceStatus (ctx.TryGetQueryStringValue "deviceId")
    match deviceStatus with
    | Ok info -> return! json info next ctx
    | Error err -> return! RequestErrors.BAD_REQUEST $"{err}" next ctx
}

let api: HttpHandler = GET >=> route "/device/status" >=> warehouseApi
// GET /device/status?deviceId=12  → 200 {"deviceId":12,"status":"ACTIVE"}
// GET /device/status?deviceId=152 → 400 NoSuchDeviceId 152
Look how the layers stack: a DU for every way the request can fail (chapter 07), taskResult { } to unwrap async + Result in single let! steps (chapters 09+12), and a thin handler that maps Ok/Error to HTTP codes. routef "/device/status/%i" gives type-checked URL parameters; ctx.BindModelAsync<'T>() binds JSON bodies.

HTML without templates: the view engine

C# lens

Mental mapping from MVC/minimal APIs: controller + [HttpGet("…")] → GET >=> route "…"; model binding → BindModelAsync / routef; IResults → handlers like json, text, RequestErrors.*; middleware pipeline → unchanged, it's still ASP.NET Core underneath. Dependency injection still exists, but most "services" become plain function parameters.

Gotcha — handler order matters in choose

choose evaluates top to bottom and takes the first handler that produces a response. Put your most specific routes first and catch-alls (404 handlers) last — a leading wildcard route will eat every request, and nothing will look "wrong" except that other routes never fire.

What does GET >=> route "/x" >=> text "hi" express?
Each piece is an HttpHandler; >=> (Kleisli composition) chains them so each gets a chance to continue or bail. Routing, verbs and responses are all the same abstraction.
Chapter 14

Testing F#: types first, then tests

F# flips the testing pyramid: the compiler already proves what a third of your C# unit tests used to check (nulls, missing cases, invalid states). What's left gets tested with less ceremony — tests as values, dependencies as functions, and FsCheck generating thousands of inputs you didn't think of.

Your first line of defense is the type system

fsxTests you no longer need to write
// private constructor: invalid emails cannot exist, anywhere, ever
type ValidatedEmail =
    private | ValidatedEmail of string

    member this.Value = match this with ValidatedEmail e -> e

    static member TryCreate (raw: string) =
        if raw.Contains "@" then Ok (ValidatedEmail raw)
        else Error "Invalid email!"

let sendEmailSafe message (email: ValidatedEmail) = Ok "Sent message"

// let direct = ValidatedEmail "anything"        // ✗ won't compile — private
ValidatedEmail.TryCreate "isaac@email.com"
|> Result.bind (sendEmailSafe "Welcome!")
"Null email", "unvalidated email reaches sender", "wrong argument order" — entire test classes from your C# suites are now compile errors. Combine with exhaustive matching (delete a DU case handler and the build warns) and the tests you still write are about behavior, not plumbing.

Expecto: tests are just values

Program.fsListings 14.3–14.4 — a test list, including generated tests
open Expecto

let musicTests =
    testList "Music tests" [
        test "My guitar gently weeps" {
            let output = play Guitar
            Expect.equal output "Wah wah" "Guitar sound is incorrect"
        }

        if System.Environment.GetEnvironmentVariable "CI_SERVER" <> null then

                | [| a; b; expected |] ->

            }
    ]

[<EntryPoint>]

No [Test] attributes, no fixture classes: a test is a value, a suite is a list, and the test project is a console app you dotnet run. Because they're values, you can build them with ifs and fors — data-driven tests with zero framework features. (Prefer staying mainstream? xUnit + FsUnit work fine in F# too.)

FsCheck: properties, not examples

fsxProperty-based testing — let the machine find your edge cases
#r "nuget: FsCheck"
open System
open FsCheck

let flipCase (text: string) =
    text
    |> Seq.map (fun c -> if Char.IsUpper c then Char.ToLower c else Char.ToUpper c)
    |> Seq.toArray
    |> String

// custom generator: only letters and spaces, never empty
type Word = Word of string
type Arbitraries =
    static member Word () =
        { new Arbitrary<Word>() with
            override _.Generator =
                Gen.elements ([ 'a' .. 'z' ] @ [ 'A' .. 'Z' ] @ [ ' ' ])
                |> Gen.arrayOf
                |> Gen.filter (Array.isEmpty >> not)
                |> Gen.map (String >> Word)
        }

// instead of asserting examples, assert LAWS that must hold for ALL inputs:
type Properties =
    static member sameNumberOfLetters (Word original) =
        (flipCase original).Length = original.Length

    static member changesCase (Word original) =
        Seq.zip (flipCase original) original
        |> Seq.forall (fun (a, b) ->
            if Char.IsLetter a then Char.IsUpper a <> Char.IsUpper b else true)

    static member doesNotChangeText (Word original) =
        String.Compare (flipCase original, original, StringComparison.OrdinalIgnoreCase) = 0

let configuration = { Config.Quick with Arbitrary = [ typeof<Arbitraries> ] }
Check.All<Properties> configuration   // runs 100 random inputs per property
Properties.sameNumberOfLetters – Ok, passed 100 tests. Properties.changesCase – Ok, passed 100 tests. Properties.doesNotChangeText – Ok, passed 100 tests.
FsCheck generates randomized inputs (here via a custom Word generator limited to letters and spaces — see the book's Arbitraries type) and, on failure, shrinks to the minimal counterexample. Break flipCase so it skips the letter 'e' and FsCheck hands you the failing input "e" — not a 40-character random string. Properties + types + a few example tests: that's the F# testing stack.
C# lens

Everything here exists for C# (FsCheck works there; so do xUnit theories) but fights the grain: stub lambdas need delegate types, generated tests need special framework support, and the type system can't carry as much proof. In F# the language itself is the test framework's biggest feature.

Gotcha — don't test the compiler

Arriving from C#, you'll instinctively write null-checks tests, "throws when invalid" tests, and case-coverage tests. Pause first: can a type make that test impossible instead? A test you never write is cheaper than a passing one — spend the saved budget on property tests for actual logic.

Checkpoint
An FsCheck property fails. What does "shrinking" give you?
Shrinking repeatedly simplifies the failing input while the property keeps failing, so instead of debugging "xKpQ zzT e9" you debug "e". It's the feature that makes property testing practical.
