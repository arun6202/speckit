The business problem

01
Oracle (~50 tables, system of record)
  → F# ETL project (.fsproj)  — full load Oracle→ES; ALSO the lineage authority
     → Elasticsearch target index (denormalized; ~150M docs)
        → C# Web API (.csproj) — exposes ES as Swagger endpoints, by module
           → consumers — abstracted from ES; believe they query Oracle

Realtime arm:
Oracle GoldenGate CDC → Kafka → temp ES index → merge/upsert → target ES index

Defects arrive as Jira tickets across prod and non-prod. There is no reliable documentation. The abstraction is the trouble: a consumer thinks they query Oracle, but reads an analyzed, denormalized, possibly stale ES document. Every defect is a gap between the felt contract (Oracle-like) and the real substrate (the ES doc and the path that filled it). Troubleshooting re-derives the lineage the abstraction hides — per ticket, without a spec that doesn't exist.

lightbulb

The thesis: descent, not spec

02

Do not write a big-bang spec / SDD pass first — modeling 50 tables, an ES DSL, the API, and the CDC path before the first ticket is debt that rots on the next code change. Instead:

  • JIT, not big-bang. Each defect pulls exactly the context it needs from the codebase.
  • The system documents itself one ticket at a time. Every resolution leaves residue: a lineage fragment, a property test, a knowledge concept.
  • Inference is cheaper than authorship. Lineage already lives in the fsproj and the C# query builder; read it on demand.

The name "The Descent" encodes it: start at the surface symptom (the API response), drill down toward ground truth (Oracle), stop at the depth where the bug lives — the opposite motion to SDD, which ascends, constructing a model before touching anything.

schema

Core concepts

03
  • System of Record (SoR) = Oracle. Ground truth. SoR wrong ⇒ a data defect (escalate), not a code defect.
  • System of Reference = Elasticsearch. Derived truth the consumer reads; drifts via a batch transform bug or a realtime path that arrived late, out of order, or never.
  • The abstraction gap. Consumers query the API as if it were Oracle; it serves ES. Most "API is wrong" tickets are this gap.
  • Lineage = a lookup from the ETL fsproj (its compile order is the index of ETL meaning), read via a subagent — never inferred fresh.
stairs

The Descent — six rungs, gate-based

04

Each rung is a yes/no gate. Clear it → descend (load the next layer). Fail it → convict and stop. A green gate is the only permission to load deeper context. Most tickets convict at rungs 1–3.

#RungGateConvicts as
1Triage & scopeMaps to a known endpoint + key?(bounce if not actionable)
2Reproduce & validate; if zero hits, SHRINKMalformed / valid-but-empty / wrong value?InvalidRequest / → Shrink / descend
3Lineage (ETL fsproj; reads C# ⚠️)API field bound to the right ES field?ContractDrift
4System of record (Oracle)Oracle value correct?SorDataIssue (escalate) / descend, drop Oracle
5Batch reconcileTransform output == target/expected?TransformDefect / descend
6Realtime traceWhere did the change stop?RealtimeStale/Drop/MergeReorder
7Verdict reflectionCause unique? Property fails-on-bug?accept / revise

The stopping rule is the point: lazy, depth-first, prune-as-you-go. You never hold all layers at once. Per-rung detail: .claude/skills/pipeline-descent/rungs/.

The Shrink — the centerpiece

05

Problem: a valid request searches the right fields/values/combination and returns zero hits when data should exist.

Reframe: the empty query is a failing counterexample. Bisect its predicates to the 1-minimal subset that still returns zero — that's the culprit. This is delta debugging (ddmin, Zeller & Hildebrandt 2002) and is identical in spirit to FsCheck shrinking. (The technique was the user's own idea; the prior instance formalized it.)

Algorithm: ddmin over Predicate list — divide (n=2), test subsets/complements, recurse into whichever still returns zero, double granularity, finish one-by-one to guarantee minimality. Impl: fsx/Descent.Shrink.fsx.

Classify why — test in this order (by base rate)

#CauseDiagnostic
1Analyzer / term-vs-match_analyze; use match on text, term on text.keyword
2Case (term is case-sensitive)case_insensitive:true (≥7.10) or lowercase normalizer
3minimum_should_match flipset explicitly; tag clauses with _name → matched_queries
4Nested scopewrap in nested+path; inner_hits
5Mapping / field absence_field_caps?fields=f, then _mappings
6Range / TZ / alias / routing_validate/query?rewrite=true; check alias write-index

Diagnostic triad: _analyze · _validate/query?rewrite=true · _explain/<known-good-id> (the id comes free from lineage). Watch max_clause_count (4096 on 8.x) — shrink logical predicates, not expanded clauses.

bolt

The Realtime trace

06

Problem: a stale document. Don't re-check Oracle and target ES — walk the event path and find the hop where the change stopped: Oracle → Kafka → temp ES → target merge.

HopQuestionEvidence
OracleRow changed & committed?value + commit time
GoldenGate/KafkaMessage at the key, in order?OGG envelope: op_type, op_ts (replay-stable), pos, primary_keys, ${csn}; key by ${primaryKeys}
ConsumerConsumed?consumer-groups --describe → LAG
Temp ESLanded?GET temp/_doc/<id>
Target mergeApplied, in order?external version / _seq_no
tips_and_updatesBonus tip — prove arrival
Topic keyed by business key ⇒ read one message deterministically (--partition P --offset O --max-messages 1), follow the op_ts/pos/csn trail; the hop where it goes cold dropped the change.

The reorder masquerading as staleness: last-write-wins lets an out-of-order replay overwrite newer data. Fix: version_type=external keyed on CSN/SCN so a lower version can't overwrite a higher. Impl: fsx/Descent.Realtime.fsx.

gavel

How issues resolve

07

RootCause is a closed set (a DU); every ticket resolves to exactly one: InvalidRequest · AnalyzerMismatch · CaseMismatch · ShouldFlip · NestedScope · MappingIssue · ContractDrift · SorDataIssue · TransformDefect · RealtimeStale · RealtimeDrop · MergeReorder. (fsx/Descent.Domain.fsx.)

Reflection (rung 7): critique the cause vs evidence, re-probe with an independent signal, and require the regression property to FAIL on the bug and PASS after the fix. If it can't be made to fail on the bug, the bug isn't understood.

Residue (required — "no residue, not done"): a property test in CI, a lineage fragment, and an OKF concept. Documentation becomes a workflow gate, not a deferred chore.

functions

The F# discipline (identity law)

08

Diagnostic tooling is F# with strict functional discipline. Non-negotiable; any C# pattern in F# is a ⚠️ to flag.

  • parse-don't-validate — boundary returns a parsed type; illegal states unrepresentable. ReadOnly<'conn> has no execute/index — a write is unrepresentable, not merely checked.
  • DUs over classes; single-case DUs for primitives (BusinessKey of string).
  • Result over exceptions on every Oracle/ES/Kafka call.
  • types as proofs · typed telemetry as data · pure Planner / effectful Runner.
reportThe one ⚠️ C# boundary
lineage is the only function that reads the C# Web API. It converts controllers/DTOs/Swagger into immutable LineageEdge values + the known-good EsId. Nothing class-shaped, nullable, or exception-based escapes it.

Why F#: the user treats type discipline as a survival strategy — "a predicate is a proposition; a refined value is its proof; the pipeline is a proof-carrying dataflow graph." Honor it.

Claude-native mechanics + 6 reliability patterns

09

Progressive disclosure (context per rung): T0 ticket · T1 endpoint→index · T2 lineage subgraph + EsId · T3 transform + SoR row + Kafka message. Never preload all 50 tables.

Context pruning (a green gate is a forget signal): drop the contract, the other tables, Oracle, the ETL source as each is ruled out. This is what most "reliability" advice omits.

Primitives: a SKILL.md skill (progressive disclosure, <500-line body) · a lineage-resolver subagent (isolated reading) · a PreToolUse hook (deny writes) · plan mode · per-ticket evidence files.

The six patterns, mapped — with the cost the generic version omits

Beyond the six, this kit adds context pruning and a typed stopping rule — what keeps the patterns from compounding into a slow loop.

hub

Knowledge capture as OKF

10

OKF (Open Knowledge Format, Google Cloud, 2026-06-12) formalizes the LLM-wiki pattern: a directory of markdown concepts with YAML frontmatter, cross-linked into a graph. Only type is required; common set: type, title, description, resource, tags, timestamp. index.md per folder; log.md for history. The kit's residue is a conformant bundle in knowledge/.

Why it changed the dynamics: knowledge stops being exhaust and becomes substrate — portable, decoupled from producer and consumer. N×M → N+M integration; model-agnostic (fits the user's multi-model habit); documentation becomes a workflow gate; the human role shifts author→curator (watch rubber-stamping); a new asset appears whose health gates agent capability.

linear_scaleThe seam to hold
OKF is the agent/human-readable context layer (meaning, joins, runbooks, lore). ODCS/ODPS/OpenLineage are machine-enforceable contracts. Complementary: a concept's resource: links to the ODCS artifact, never duplicates it. OKF does not validate drift.

Rule: .claude/rules/knowledge-capture-okf.md. Bundle: knowledge/README.md. Emitter: fsx/Descent.Okf.fsx.
