The Descent.

A per-ticket protocol for an undocumented pipeline. Infer context just-in-time from the codebase, drill the lineage only as far as the bug lives — and when a valid search returns nothing, shrink the query until the culprit field confesses.

00 — Doctrine

Don't design a spec. Run a descent.

There is no reliable documentation, and you won't write one up front. Each defect pulls exactly the context it needs out of the codebase, and resolving it leaves behind a durable fragment — a lineage edge, a property test, a rule. The system documents itself, one ticket at a time.

Two truths the protocol turns on

  • System of Record (Oracle). Ground truth. If the SoR is wrong, the pipeline was faithful and the ticket is a data defect, not a code defect — the descent escalates, it doesn't patch ES.
  • System of Reference (Elasticsearch). Derived truth the consumer actually reads. It drifts from the SoR through a batch transform bug or a realtime path that arrived late, out of order, or never.

The abstraction that generates your tickets

The consumer queries the C# Web API and believes they are querying Oracle. They aren't — they read an ES index shaped to feel relational. Every defect is a gap between that felt contract (Oracle-like) and the real substrate (an analyzed ES document, possibly stale). Troubleshooting re-derives the lineage the abstraction hides.

Consumer request→ C# Web API→ ES target index↑ merge temp index← Kafka← GoldenGate CDC← Oracle (SoR)

The givens — decisions are settled, so wire to them

  • Tooling is F# .fsx. Scripts can query Oracle and ES directly, in both prod and non-prod, read-only. That means reproduction and reconciliation happen in-tool — no console detours.
  • Lineage is a lookup, not an inference. The ETL fsproj that manages the full Oracle→ES load is the authoritative lineage source. The descent reads it; it doesn't guess.
  • Staleness is proven by arrival. A stale doc is diagnosed by walking Oracle → Kafka message → temp ES — checking at each hop whether the change actually arrived.
F# identity law — in force this session The descent tooling is F#: parse-don't-validate at every boundary, types as proofs, DUs over classes, Result over exceptions, typed telemetry as data. The C# Web API is survival-income territory; its controllers, DTO classes and exception filters are an ⚠️ un-disciplined zone. We don't import its patterns — we re-parse its OpenAPI + query builder back into F# proof types at the boundary, and that boundary is always marked.
01 — The Descent

Six rungs. Stop at the first that convicts.

Each rung is a gate: one yes/no probe that clears the layer (descend) or convicts it (stop, found). You never load a lower rung's context until the gate above is green. Most tickets convict at rung 1–3 and never touch Oracle, ETL, or Kafka.

verified / ground truth contract / consumer / query batch / structural lineage realtime / CDC path convicted defect
Triage & scope layer · intake

Parse the Jira ticket into a typed Scope: env (prod / which non-prod slot), endpoint & module, record key, the consumer's request, observed-vs-expected. Pruning starts here — endpoint → module → one ES index → its lineage subgraph (looked up from the ETL fsproj).

Gate: ticket maps to a known endpoint & key? no → bounce as unactionable.
Reproduce, validate — and if empty, shrink layer · consumer / query

Replay the consumer's exact request against the scoped env. Parse it against OpenAPI (parse, don't validate). If it returns the wrong value → continue down. If it's a valid request that returns not found when data should exist → enter The Shrink: bisect the predicates until the culprit field/value confesses.

Gate: malformed request → InvalidRequest. valid-but-empty → shrink → classify. wrong value → descend.
Re-derive lineage from the ETL fsproj layer · lineage · ⚠️ reads C#

Look up: API param → ES query → ES field (from the C# query builder ⚠️), then ES field → Oracle table.column (from the ETL fsproj). Confirm the felt Oracle-contract still binds the right ES field. Output is re-parsed into typed LineageEdges; nothing C#-shaped escapes.

Gate: binding correct? no → ContractDrift. yes → descend.
Check the System of Record layer · oracle SoR

Query Oracle directly (the .fsx can) for the keyed record along the lineage edge.

Gate: SoR correct? no → SorDataIssue (escalate to data owner). yes → SoR fine, API wrong ⇒ drift is below the API, above Oracle. Descend, and drop Oracle from context.
Reconcile the batch transform layer · fsproj ETL

Re-run the transform for this one record; diff produced ES doc vs live target. A mismatch is a deterministic, testable transform defect.

Gate: output matches target & expected? no → TransformDefect. yes → batch innocent; drift entered via realtime. Descend.
Trace the realtime CDC path layer · GG · kafka · temp · merge

Follow the key: Oracle → Kafka message → temp ES → target merge. The failure is one of arrived late, arrived out of order, or never arrived. → Realtime trace.

Gate: RealtimeStale · RealtimeDrop · MergeReorder.
The stopping rule is the whole pointA green gate is permission to load the next layer's context, nothing more. You're never holding all six layers — in your head or the model's window — at once. Lazy, depth-first, and it prunes as it goes.
02 — The Shrink · the centerpiece

When a valid search finds nothing, shrink it.

A request from the sample list, right fields, right values, right combination — and zero hits. Don't give up and don't eyeball it. Bisect the query predicate-by-predicate until the data reappears, isolating the exact field/value/combination that kills the match. This is delta debugging, and it's the same instinct as FsCheck shrinking a failing case to its minimal reproducer.

The reframeThe empty query is the failing counterexample. The shrink reduces the predicate set to the 1-minimal subset that still returns nothing — the culprit. Then three ES diagnostic APIs name why.

The algorithm — ddmin, not linear poking

The manual instinct ("peel down to ID, add fields back one at a time") is linear — O(n) probes. The tool runs Zeller's ddmin: divide the predicate set, test subsets and complements, recurse into whichever still returns empty, doubling granularity until it reaches a 1-minimal culprit set. Binary-search fast in the common case; final pass deletes one-by-one to guarantee minimality.

03 — F# kit · .fsx

Small, typed, read-only probes.

Every probe returns a Result or a DU, threads typed telemetry, and never writes. Pure planner decides the next probe; effectful shell runs it. The shrink is ddmin over a predicate set; the reconciler walks the realtime hops.

Domain — the world parsed into closed sets

Descent.Domain.fsx
// Single-case DUs kill primitive obsession; Env is a proof, not a string
type Env = Prod | NonProd of slot:string
type BusinessKey = BusinessKey of string
type EsId = EsId of string

// A query predicate is a closed set — each one a "delta" the shrink can drop
type MatchKind = Term | Match | Phrase | Range | Nested of path:string
type Predicate =
    { Field:string;  Value:string;  Kind:MatchKind;  Name:string }   // Name → _name → matched_queries

// The shrink oracle. Three-valued: Unresolved keeps us honest about flaky probes
type Probe3 = Found | NotFound | Unresolved

// One closed set of causes. classify : evidence -> exactly one of these
type RootCause =
    | InvalidRequest   of field:string * rule:string
    | AnalyzerMismatch of field:string * indexTokens:string list * queryTokens:string list
    | CaseMismatch     of field:string * sent:string * stored:string
    | ShouldFlip       of clause:string
    | NestedScope      of path:string
    | ContractDrift    of apiField:string * esField:string
    | SorDataIssue     of table:string * key:BusinessKey
    | TransformDefect  of field:string
    | RealtimeStale    of topic:string * lagMs:int
    | RealtimeDrop     of stage:Stage * key:BusinessKey
    | MergeReorder     of key:BusinessKey

The shrink — ddmin over predicates

Descent.Shrink.fsx
// Minimise the failing (empty) predicate set to a 1-minimal culprit set.
// `probe ps = NotFound` means "this subset still returns zero hits".
let ddmin (probe: Predicate list -> Probe3) (failing: Predicate list) =
    let stillEmpty xs = (not (List.isEmpty xs)) && probe xs = NotFound
    let rec loop preds n =
        if List.length preds < 2 then preds
        else
            let size  = max 1 (List.length preds / n)
            let parts = preds |> List.chunkBySize size
            // keep the smallest complement that still reproduces the empty result
            let reduced =
                parts |> List.tryPick (fun part ->
                    let comp = preds |> List.filter (fun p -> not (List.contains p part))
                    if stillEmpty comp then Some comp else None)
            match reduced with
            | Some smaller                       -> loop smaller 2                // recurse, reset granularity
            | None when n < List.length preds -> loop preds (min (List.length preds) (n*2))
            | None                              -> preds                       // 1-minimal: the culprit set
    loop failing 2

// Then classify WHY the minimal culprit empties the result.
let classify env idx goodId (culprit: Predicate) : Async<RootCause> = async {
    match culprit.Kind with
    | Term ->
        let! caps = Es.fieldCaps env idx culprit.Field
        let! toks = Es.analyze   env idx culprit.Field culprit.Value
        return Diagnose.termOnField caps toks culprit       // → AnalyzerMismatch | CaseMismatch
    | _ ->
        let! ex = Es.explain env idx goodId (Query.ofPredicate culprit)
        return Diagnose.fromExplain ex culprit }

04 — Realtime trace

Prove arrival, hop by hop.

A stale doc isn't diagnosed by re-checking Oracle and target ES. You walk the event path and find the hop where the change stopped: Oracle → Kafka message → temp ES → target merge.

Oracle row→ GoldenGate CDC→ Kafka (keyed by PK)→ temp ES doc→ merge target ES doc

What each hop proves, and how

HopQuestionEvidence to read
OracleDid the row actually change & commit?row value + commit time; the reporter may have expected an uncommitted value.
GoldenGateWas the change captured to Kafka?OGG envelope: op_type (I/U/D/T), op_ts (source trail, replay-stable), pos (seqno+RBA), primary_keys.
KafkaArrived with the right key & order?key = ${primaryKeys} → same partition in commit order; read by partition+offset; compare after-image.
ConsumerWas it consumed?consumer-groups --describe: CURRENT-OFFSET, LOG-END-OFFSET, LAG per partition.
Temp ESDid it land?GET temp/_doc/<id> or by-key search; deserialization/schema errors stop it here.
Target mergeDid the upsert apply, in order?target _version / external version / _seq_no; an older CDC event must be rejected, not win.

The ordering defect that masquerades as staleness

If the target merge is last-write-wins, an out-of-order CDC replay overwrites a newer value with an older one — a "stale" doc that's really a reorder. The fix is external versioning keyed on the source CSN/SCN: index with version_type=external so a lower external version can never overwrite a higher one. Elastic's optimistic-concurrency primitives (if_seq_no & if_primary_term) cover the in-cluster case; external versioning covers "Oracle is the version authority."

expose the CSN deterministically (OGG metacolumn template)
# There is no default csn field. Emit one explicitly:
gg.handler.NAME.format.metaColumnsTemplate=${objectname[table]},${optype[op_type]},${csn[csn]},${position[pos]}
# key every change to a row onto one partition, in commit order:
gg.handler.kafkahandler.keyMappingTemplate=${primaryKeys}
★ Bonus tip — prove arrival between Oracle, the Kafka message, and temp ES Because the topic is keyed by the business key, you can read the one CDC message deterministically and compare its image + op_ts/pos/csn to the Oracle row — then check the same id in temp ES. The hop where the op_ts/pos/csn trail goes cold is the stage that dropped it.
# 1. read exactly one message at the business key's partition+offset
kafka-console-consumer.sh --bootstrap-server $B --topic $T \
  --partition $P --offset $O --max-messages 1 \
  --property print.key=true --property print.timestamp=true

# 2. is the consumer keeping up?  LAG should be ~0 if the merge is healthy
kafka-consumer-groups.sh --bootstrap-server $B --describe --group $G

# 3. did the same id reach temp ES?  (op_ts here should match the Kafka op_ts)
GET temp_idx/_doc/<esId>?_source=op_ts,csn,after

Version caveat: envelope field names are stable across OGG 12.3→19.1→26, but confirm ${csn} availability and whether your handler runs in op mode (one message per operation, key = PK) vs tx mode (concatenated, NULL key — which breaks per-key reads). Also confirm full supplemental logging, or update/delete before-images may be partial.

05 — Claude-native mechanics

Hold just enough, and no more.

The descent is also how you drive the model. Progressive disclosure loads context per rung, pruning drops what a green gate ruled out, and skills/subagents/hooks encode the discipline so it isn't re-explained each session.

Progressive disclosure — context arrives per rung

T0intake
The ticket only. Env, endpoint, key, request, expected/actual.
T1map
Endpoint → module → ES index. One row of the routing table.
T2edge
The lineage subgraph + known-good EsId. A few edges, looked up from the ETL fsproj — not the whole catalog.
T3source
Transform code + the SoR row + the Kafka message. The deepest tier — only for genuine pipeline defects.

Context pruning — a green gate is a forget signal

  • Request validated → drop the OpenAPI contract. Shrink converged → drop the innocent predicates.
  • Lineage edge confirmed → drop the other 49 tables and the rest of the routing table.
  • SoR confirmed correct → drop Oracle entirely; the bug is strictly downstream.
  • Batch transform clean → drop the ETL source; the surface is now only the realtime path.

- Run THE DESCENT. Stop at the first gate that convicts. Don't load a lower
  tier until the gate above is green.
- Valid request, zero hits → run THE SHRINK (ddmin) before anything else.
  Test analyzer/term-vs-match FIRST, then case, then minimum_should_match.
