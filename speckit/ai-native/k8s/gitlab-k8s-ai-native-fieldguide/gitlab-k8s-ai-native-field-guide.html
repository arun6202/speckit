Overview · the platform

Git holds the truth. The pipeline proves it. The cluster reconciles to it. Agents now ride the loop.

Modern delivery is one continuous loop with two planes. The delivery plane — GitLab — turns a commit into a verified, signed artifact. The runtime plane — Kubernetes — continuously converges the live cluster onto the declared desired state. In 2026 a third thing cuts across both: AI, which now authors and fixes pipelines, diagnoses and operates clusters, and runs as first-class workloads on the cluster itself. This guide maps that whole picture — and flags what's genuinely state-of-the-art right now. It is deliberately stack-agnostic; tools are named as exemplars.

The delivery loop

Everything below is a stop on one loop. Code becomes truth in Git; CI proves and packages it; GitOps pulls it into the cluster; the cluster runs and self-heals; observability feeds the next change. The shift that defines the era: deployment is no longer a push from a pipeline but a pull the cluster performs against Git.

Delivery plane · GitLab CI/CD

Turn a commit into a proven, signed artifact.

A GitLab pipeline is a directed graph of jobs that build, test, scan, and package every change before it can ship. The 2026 platform adds two things that matter: reusable components that kill copy-pasted YAML, and agents that set up, modernize, and repair pipelines for you.

The pipeline model

Jobs belong to stages that run in sequence by default; needs: turns the pipeline into a DAG so independent jobs start as soon as their inputs are ready. rules: and workflow: decide when a job or pipeline runs; artifacts and cache pass state between jobs; environments model where a version is deployed and gate production behind manual approval.

Stages & jobsmodel

Ordered stages of parallel jobs. The unit of work is a job running a script in an image.

needs: (DAG)speed

Break the strict stage order — start a job the moment its dependencies finish. Shorter critical path.

rules / workflowcontrol

Conditional execution by branch, MR, tag, file changes, or variables. Replaces legacy only/except.

Environmentsdeploy

Track deployed versions per environment; protect prod with approvals; tie into release and rollback.

Runners — where jobs execute

Runners pick up jobs and run them. The modern pattern is the Kubernetes executor: each job gets its own ephemeral pod that is created on demand and destroyed after — clean builds, automatic resource cleanup, no persistent host to babysit. The runner deployment itself becomes a GitOps artifact when managed by Flux.

CI/CD Components & the Catalog

A component is a reusable, versioned unit of pipeline configuration — a function for pipelines, with typed inputs and pinned versions. Publish them to the CI/CD Catalog so teams discover and reuse instead of reinventing. This is the SOTA answer to YAML sprawl.

# Consume a versioned component — pinned, parameterized, reviewable
include:
  - component: $CI_SERVER_FQDN/my-group/components/docker-build@1.2.0
    inputs:
      image: my-app
      dockerfile: Dockerfile.prod

# Authoring one (templates/docker-build.yml)
spec:
  inputs:
    image: { type: string }
    dockerfile: { type: string, default: Dockerfile }
---
build:
  image: docker:27
  script:
    - docker build -f $[[ inputs.dockerfile ]] -t $[[ inputs.image ]] .

Security scanning — shift left, gate the merge

GitLab folds application-security scanners directly into the pipeline so findings surface in the merge request, not weeks later. Treat them as gates, not reports.

SASTcode

Static analysis of source for vulnerable patterns. Now paired with agentic resolution that drafts ready-to-merge fixes.

Dependency & Containersupply

Scan third-party libraries and image layers for known CVEs; produce a dependency inventory.

Secret Detectionleaks

Catch committed tokens and keys before they reach history. Pair with rotation.

DAST & IaCruntime/config

Dynamic scanning of a running app, plus IaC scanning of Terraform/Kubernetes manifests for misconfig.

Supply-chain integrity

The pipeline is the right place to make artifacts trustworthy: generate an SBOM (CycloneDX) of what's inside, sign the image with Cosign (keyless OIDC), and attach SLSA provenance attestations describing how it was built. The cluster later verifies all of this at admission (see Patterns).

AI in the pipeline

GitLab Duo agents now stand up a working pipeline from a repo, convert/modernize legacy CI, fix a failing pipeline, and auto-resolve SAST findings with ready-to-merge code. Useful acceleration — but the merge stays human-owned (see the AI-Native tab).

Runtime plane · Kubernetes

A convergence engine for declared state.

You don't tell Kubernetes how to run your system — you declare what you want, and controllers work continuously to make reality match. Understand the core objects, how traffic gets in (now via the Gateway API), how things scale, and how workloads stay healthy.

Core workload objects

Podatom

The smallest deployable unit — one or more containers sharing network and storage. You rarely create these directly.

Deploymentstateless

Declarative rollout/rollback of replicated stateless pods via ReplicaSets. The default for web/API services.

StatefulSetstateful

Stable identities and ordered, persistent storage for databases, brokers, and clustered systems.

DaemonSetper-node

One pod per node — log shippers, metrics agents, CNI, GPU device tooling.

Job / CronJobbatch

Run-to-completion tasks and scheduled work — migrations, ETL, training jobs.

ConfigMap / Secretconfig

Externalized configuration and sensitive values. Keep Secrets encrypted; never commit plaintext to Git.

Getting traffic in — the Gateway API era

Major 2026 shift

The community ingress-nginx controller was retired in March 2026 (repository read-only; no further releases, bug fixes, or CVE patches). The Gateway API — with GA core resources GatewayClass, Gateway, and HTTPRoute — is the successor, offering role separation, header/traffic matching, and cross-namespace routing without annotation sprawl. The legacy Ingress API itself remains but is feature-frozen; ingress2gateway assists migration.

Gateway API implementations to evaluate include Envoy Gateway, Istio, Cilium, Traefik, Kong, kgateway, Contour, and NGINX Gateway Fabric. Service still provides stable in-cluster addressing (ClusterIP) and basic external exposure (LoadBalancer); the Gateway layer handles L7 routing on top.

Packaging — Helm & Kustomize

Helmtemplating

Charts package and parameterize manifests via values; great for redistributable apps and dependencies. GitOps tools consume it (Flux HelmRelease, Argo server-side render).

Kustomizeoverlays

Template-free base + overlays for per-environment patches. Built into kubectl; idiomatic for "same app, different env."

Extending the API — operators & CRDs

A CustomResourceDefinition adds new object types; an operator is a controller that reconciles them, encoding day-2 operational knowledge (backups, failover, upgrades) as software. Most of the AI-serving and GitOps tooling in this guide ships as operators with their own CRDs.

Scaling & resilience

HPA / VPApod scaling

Horizontal scaling on CPU/memory/custom metrics; vertical right-sizing of requests. The baseline elasticity.

KEDAevent-driven

Scale on queue depth, stream lag, or external signals — and scale to zero when idle. Key for bursty and AI workloads.

Karpenter / Cluster Autoscalernode scaling

Provision and consolidate nodes to fit pending pods — including GPU node pools — for cost-efficient capacity.

Probes & PDBhealth

liveness/readiness/startup probes drive healing and safe rollouts; PodDisruptionBudgets protect availability during disruptions.

Production defaults that aren't optional: resource requests/limits, all three probe types, a PodDisruptionBudget, topology spread + anti-affinity, and a non-root, least-privilege security context. Details in Patterns.

The bridge · GitOps & delivery

Stop pushing deploys. Let the cluster pull the truth.

GitOps makes Git the single source of truth and puts a controller inside the cluster that continuously reconciles live state to declared state — correcting drift automatically. It's how the delivery plane and runtime plane connect, and in 2026 it's the mainstream model.

The reconciliation loop

Desired state
Manifests / Helm / Kustomize, versioned in Git (or an OCI artifact)
⇄continuously compare & converge · correct drift
Live state
What's actually running in the cluster, right now

Per the OpenGitOps principles, the system is declarative, versioned & immutable, pulled automatically, and continuously reconciled. A change is a commit; a rollback is a revert; the audit trail is the Git history.

Push vs. pull

ModelHow it worksTrade-off
Push (CI deploys)The pipeline runs kubectl/helm against the cluster using stored credentials.Simple, but the pipeline holds cluster creds, there's no drift correction, and the cluster trusts an external actor.
Pull (GitOps)An in-cluster controller watches Git/OCI and applies changes itself; no inbound cluster credentials.Recommended: least-privilege, self-healing, fully auditable. Slightly more moving parts to learn.

The GitLab agent for Kubernetes

agentk (in-cluster) plus the agent server (KAS) establishes a secure, bidirectional tunnel that needs no open inbound cluster port. It supports both pull-based GitOps (with Flux) and push-based CI access, surfaces live cluster state in the GitLab UI, and provides user impersonation for scoped access.

Migrate off the old path

The legacy certificate-based Kubernetes integration is sunsetting on GitLab.com (2026). Move to the agent for Kubernetes for secure connectivity. GitLab recommends Flux for the GitOps engine, using signed OCI artifacts as the source rather than a raw Git repository.

Progressive delivery

A rolling update is the floor — it gives readiness gating but no traffic control or automated rollback. Progressive delivery adds gradual traffic shifting, metric-based analysis, and automatic promote/abort.

Argo RolloutsArgo side

A Rollout replaces Deployment with canary and blue-green strategies, AnalysisTemplate metric gates, and traffic shaping via Gateway API or a service mesh.

FlaggerFlux side

Canary, A/B, and blue-green driven by metrics, integrating with meshes (Istio, Linkerd) and ingress/gateway controllers.

Automated promotion is only as trustworthy as the metrics behind it — progressive delivery assumes a Prometheus-class metrics source and precise traffic splitting (mesh or supported gateway).

AI-native · across the platform

Agents build it, agents operate it, and the cluster runs the models.

AI-native means three distinct things in 2026: AI in the delivery platform, AI operating the cluster, and AI as the workload the cluster runs. All three are real and production-adjacent — and all three keep a human on the irreversible decisions.

A · AI in the delivery platform

GitLab Duo Agent Platform (GA) moves from 1:1 code assistance to many-to-many team-agent collaboration across the SDLC.

Agentic Chatinterface

Multi-step reasoning with full project context — issues, MRs, pipelines, security findings — in the Web UI and IDEs.

Agentsworkers

Credits & governancecost control

Per-feature model selection, subscription- and per-user spend caps, and usage visibility for safe enterprise rollout.

B · AI operating the cluster (AIOps)

A new class of tools brings Observe → Reason → Act to operations — and most expose an MCP server so any assistant can drive them.

k8sgptdiagnose

CNCF project: 20+ built-in analyzers scan the cluster; --explain sends anonymized context to an LLM for plain-English root cause. Ships an MCP server for Claude/MCP clients.

kagentoperate

Solo.io, CNCF Sandbox: an agentic framework that runs in-cluster, supports MCP and A2A, and executes constrained, auditable remediations — not a magic self-healing button.

HolmesGPTinvestigate

Root-cause analysis from alerts, pulling Prometheus, logs, and external tools — purpose-built for incident investigation.

kubectl-ai · Botkubeassist

Natural-language kubectl, and alert triage with suggested commands inside Slack/Teams.

C · AI workloads on the cluster

Serving the models

vLLMengine

The 2026 default inference engine: PagedAttention for efficient KV-cache memory and continuous batching for throughput. The runtime under most stacks.

KServeserving plane

Standardized serving control plane: InferenceService / LLMInferenceService, scale-to-zero, canary rollout, and model lifecycle/governance.

llm-ddistributed

Kubernetes-native distributed inference: KV-cache-aware routing, prefill/decode disaggregation, and the Gateway API Inference Extension for cluster-wide efficiency.

vLLM production-stackreference

Reference K8s deployment: prefix-aware request routing and KV-cache sharing (LMCache) to scale from one engine to a fleet without app changes.

Scheduling the GPUs

SOTA: DRA is GA

Dynamic Resource Allocation went GA in Kubernetes 1.34 and is on by default. It replaces the count-based nvidia.com/gpu: 1 model with attribute-based claims (DeviceClass, ResourceClaim, ResourceSlice) — request a GPU by memory, MIG profile, or topology. NVIDIA is donating its DRA driver to the CNCF.

GPU sharingdensity

MIG = hardware partitions (≤7) with isolation; MPS = trusted concurrency; time-slicing = oversubscription, no isolation. Typical: MIG on inference, whole-GPU on training, time-slice on dev.

NVIDIA GPU Operatordrivers

Manages driver lifecycle, device plugin/CDI, and feature discovery. The standard way to make GPUs schedulable.

Kueuequeueing

CNCF job queueing and quota on top of the scheduler — fair sharing of scarce GPUs across teams; DRA-aware.

KAI / Volcanogang sched

Gang scheduling and topology-aware placement for distributed training (atomic all-or-nothing). KAI (NVIDIA) and Volcano (HPC/MPI).

Orchestrating the rest

Ray for distributed training/serving, Kubeflow for pipelines, KAITO for model operators, Karmada for multi-cluster federation, MLflow for tracking, and Karpenter for GPU node provisioning round out the platform.

The line humans hold

Agents draft MRs, diagnose incidents, and suggest remediations brilliantly — but a human owns the merge, the production apply, the rollout promotion, the security policy, and anything irreversible or destructive. Start agents read-only / dry-run in dev or staging; require approval for writes; scope blast radius with RBAC. An agent can open the MR; a human owns the merge. For data-sovereignty, point agents and AIOps at self-hosted model endpoints (e.g. a local vLLM/Ollama backend) so context never leaves your boundary.

Patterns & anti-patterns

What a trustworthy platform does — and what quietly breaks it.

The tools are commodities; the discipline isn't. These are the patterns that make delivery fast and safe across both planes, and the anti-patterns that turn green pipelines and "it's running" into false confidence. All stack-agnostic.

Pipeline & delivery patterns

Components over copy-pasteDRY

Centralize build/scan/deploy as versioned catalog components; consumers pin a version and pass inputs.

DAG + fail-fast gatesspeed/safety

Parallelize with needs:; run security and lint early so broken changes die cheaply.

Immutable, digest-pinned imagesreproducible

Tag by version/SHA and deploy by digest — never latest. The same artifact promotes across environments.

Ephemeral runnersclean

One pod per job on the Kubernetes executor; no shared mutable runner state.

Environments + approvalscontrol

Model dev/stage/prod; protect production with manual approval and protected variables.

Sign + attest in CIsupply chain

Cosign signature + SBOM + SLSA provenance produced in the pipeline, verified later at admission.

GitOps patterns

Separate app vs config reposstructure

Application source and deployment manifests live apart; a CI bump to the config repo triggers reconciliation.

Signed OCI as sourceintegrity

Package manifests as OCI artifacts, sign them, and have the controller deploy only verified images.

Env via overlay/dir/branchpromotion

Kustomize overlays or per-env directories; promotion is a reviewed change, not a console click.

Drift = alert + auto-correctconvergence

Out-of-band changes are detected and reverted to the declared state; surprises become signals.

Secrets, never plaintextsafety

SOPS, Sealed Secrets, or an external secrets operator — encrypted at rest in Git, decrypted in-cluster.

App-of-apps / ApplicationSetscale

Template fleets across clusters/teams from one declarative definition instead of hand-managing each.

Kubernetes production patterns

Requests & limitsfairness

Set both so the scheduler can pack honestly and one workload can't starve a node (OOM/noisy neighbor).

All three probeshealth

startup → readiness → liveness drive safe rollouts and self-healing without flapping.

Least-privilege security contexthardening

Non-root, read-only root filesystem, drop capabilities; enforce via Pod Security Admission (restricted).

Default-deny NetworkPolicysegmentation

Deny all, then allow needed flows. Closes the most common production gap (K8s Top 10).

PDB + spread + anti-affinityavailability

Survive node drains and zone loss; don't co-locate all replicas on one node/zone.

Namespaces + RBACtenancy

Isolate by team/env with least-privilege roles; no cluster-admin for routine work.

AI-workload & agent patterns

Right sharing per tierGPU economy

MIG for isolated inference, whole-GPU for training, time-slicing for dev — expressed as DRA DeviceClasses, not separate node pools.

Scale idle models to zerocost

KServe/KEDA scale-to-zero so idle endpoints don't burn GPUs; Karpenter releases the node.

Queue, don't thrashfairness

Kueue admits GPU jobs against quota; gang-schedule distributed training so partial placement can't deadlock.

Cap the agent blast radiusgovernance

Read-only/dry-run first; approval gates for writes; scoped RBAC; audit every action. No unattended prod mutation.

Anti-patterns — quietly corrosive

Delivery & supply chain

  • kubectl apply from laptops — undocumented, unauditable drift.
  • Pipeline deploys with cluster-admin creds stored in CI.
  • Deploying :latest — no reproducibility, no real rollback.
  • Secrets in CI variables or plaintext Git.
  • No security gates — scanners run but never block.
  • Snowflake runners and copy-pasted YAML everywhere.

Runtime, GitOps & AI

  • ClickOps drift — changes made in the console, not Git.
  • No requests/limits or probes — OOM, noisy neighbors, no healing.
  • Running ingress-nginx past EOL (unpatched L7 in the data path).
  • Unsigned images admitted; cluster-admin as the default.
  • nvidia.com/gpu: 1 for everything — no sharing, no scale-to-zero, GPUs idle-burning.
  • Auto-merging agent MRs or giving agents unattended prod write access.
